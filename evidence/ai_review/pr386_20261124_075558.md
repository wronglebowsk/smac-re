Findings, most important first.

1. **P1 — `scripts/m358_row_layout.py:330-333` — G9 misclassifies bit-8 setters/clearers by substring, so the “bit8” claim can stay green on wrong immediates.**  
   `sets = [r for r in hi if ",0x1" in r["ins"] and r["ins"].startswith("or")]` and `clears = [r for r in hi if ",0xfe" in r["ins"]]` match `or BYTE PTR [..],0x10`, `or BYTE PTR [..],0x100`, `and BYTE PTR [..],0xfe0`, etc. The claim is specifically “1 clear (`and [..31],0xfe`) + 3 sets (`or [..31],0x1`)”, i.e. exact high-byte bit 0. The mutant only changes `0x1` to `0x2`, so a real wrong input like `0x10` would still be counted as a bit-8 setter. This is a classifier/argument-decoding bug and makes the VERIFIED bit-8 claim non-falsifiable for a whole class of wrong instructions.

2. **P1 — `scripts/m358_row_layout.py:341-345` — G10 does not gate the prototype source→destination mapping.**  
   `okp = all(("ds:0x%x" % (proto_base + f)) in ptext and src in ptext for f, src in PROTO_STORES)` only checks that each destination address and each source token appear somewhere in the 0x64-byte window. It does not assert that `+0x141fc` feeds `+0x24`, that `+0x14208` feeds `+0x20`, that `0xff` is the immediate stored to `+0x2e`, or that the stores are in row 63 rather than another row. The NAMED claim is a mapping claim: `src +0x141fc/200/204/20c -> +0x24/25/26/27, +0x14208d -> +0x20, 0xff -> +0x2e`. A gate that only checks co-occurrence can pass with scrambled stores. MU12 reddens only because it removes the source token, not because it proves the mapping.

3. **P1 — `scripts/m358_row_layout.py:321-327` — G8 does not read the claimed “A” chain.**  
   The claim is `0x80 slots -> cand[idx] -> 0x5a73f0 -> imul 0x34`. G8 only checks that five hardcoded addresses exist, that one is `cmp DWORD PTR [ebp-0x28],0x80`, that one mentions `0x9267e4`, and that one mentions `0x34`. It does not assert that the `0x9267e4` reference is a memory load, that the loaded value is used as an index, that `0x5a73f0` is called, or that the `imul 0x34` result addresses the row array. The cited evidence line for this row is also weak (`:44,77`; line 44 is a 0x1c loop line, not the A-chain). This VERIFIED row is not actually gated as claimed.

4. **P2 — `scripts/m358_row_layout.py:287-291` and `NAMED.md:1599` — the “1,907 mem refs/227 fns” part of the field-atlas claim is not gated.**  
   G2 only asserts `field_offs == want_fields`, i.e. the set of 17 offsets. It does not assert the printed census counts `1991 refs (1907 mem) in 227 functions`. The NAMED row explicitly includes those counts and is marked `V MU2-4`, but MU2-4 only redden offset set/width/NUL properties. If the census counts were wrong, the gate would remain green. Either remove the counts from the VERIFIED claim or add a gate that reads them.

5. **P2 — `scripts/m358_row_layout.py:297-303` — G5’s “four loops = 24 iterations” is hardcoded arithmetic, not parsed from bytes.**  
   `SENT_STARTS` are constants in the script, and `iters = [(e - s) // 0x1C for s, e in SENT_STARTS]` merely checks that the constants divide to 24. The claim is that the 16 cmp sentinels are loop end checks of four real 0x1c-stride scans with 24 iterations. The instrument does not parse loop starts, loop ends, stride advances, or branch targets to prove those are loops. MU5/MU6 redden sentinel cmp/add properties, but not the loop-iteration claim. This is a measurement-definition mismatch: the prose says “loops”, the gate checks hardcoded endpoint arithmetic.

6. **P2 — `scripts/m358_row_layout.py:305-309` — G6 does not gate “0x9267e4 = 128 dwords”; it only gates refs inside a hidden 0x80-dword window.**  
   The census window is `CAND_BASE <= v < CAND_BASE + 4 * CAND_N`, with `CAND_N = 0x80`. G6 asserts 10 refs, 7 mem refs, and that mem refs contain `*4+0x9267e4`. It does not read any table bound, allocation, maximum index, or builder range that would establish 128 dwords. If the table were larger or smaller, refs outside the hardcoded window would be ignored and the gate could still pass. The claim “128 dwords” needs a gate that measures the bound from the builders or from a real table-end sentinel, not just a constant window.

7. **P2 — `scripts/m358_row_layout.py:311-319` — G7’s entry-formula assertions are partly tautological.**  
   `entry(2, 0x41) == 0x81` and `entry(1, 0x41) == 0x41` are computed by the Python `entry()` helper, not read from the disassembly. They cannot fail on any real input once `builder_shape()` passes. The claim is about the decoded entry formula in the builders. The builder-shape matcher is useful, but the formula examples should be derived from parsed immediates/shifts/masks or at least asserted against parsed constants, not against a local Python reimplementation.

8. **P2 — `NAMED.md:1603` — flags-bit8 evidence citation points to the wrong evidence line.**  
   The row cites `:16,33`. Line 16 is the `+0x30 flags` atlas row, but line 33 is the prototype store `0x0043565a mov eax,DWORD PTR [edx+0x14208]`, not the flags high-byte evidence. The actual `+0x31` rmw sites are printed around `evidence/m358_row_layout.txt:61-62`. This violates the `path:line` evidence convention and makes the claim’s evidence trail misleading.

9. **P2 — `scripts/m358_row_layout.py:269-273` — G1’s message overstates what G1 reads.**  
   G1 asserts `len(im) == 756`, `proto_base == 0x98BA54`, and the arithmetic identity `0x98BA74 == proto_base + 0x20`. It does not read a store at `0x98ba74`. The printed message says “row63 base 0x98ba54, its +0x20 store at 0x98ba74”, but the store is only gated later by G10, and even G10 does not pair it properly. This is a gate-message/claim mismatch: the gate text claims a byte-read fact that the gate does not assert.

10. **P2 — `scripts/m358_row_layout.py:247-252` — sentinel “all cmp” check does not prove the sentinel offsets contain only cmp refs.**  
   `ok_sent` checks that the number of `cmp` instructions at each sentinel offset equals the expected count, but it does not check that `len(sent[o]) == n`. Extra non-cmp immediate refs at `+0x08/+0x0c/+0x10/+0x14` would not redden G5 as long as the cmp count remains correct. The RETRACT claim says those offsets are 16 cmp sentinels, not fields; the gate should assert the full ref set at those offsets is cmp-only, or at least that there are no non-cmp refs there.
