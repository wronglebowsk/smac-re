Findings, most important first:

1. **P1 — `NAMED.md:1501` ACCEPT row is for the wrong milestone/instrument and cites the wrong evidence.**  
   The M349 block ends with:  
   `ACCEPT scripts/m349_page_writer.py PASS M347: 12/12 3fadfd6e6d26e64c x2; harness 20/20, coverage 12/12 | :55-57 | V MU0`  
   This is not M349. The shipped M349 instrument is `scripts/m349_unit_id.py`, its printed acceptance is `PASS M349: 13/13 gates`, digest `4d3c2e4ded19d620`, and harness is `scripts/m349_mutate.py` 18/18. The cited evidence lines `evidence/m349_unit_id.txt:55-57` are TABLE 2 rows for heads `64`, `128`, `133`, not an ACCEPT block. This makes the milestone’s acceptance claim unverifiable from the cited artifact and violates the “claims in NAMED.md are marked VERIFIED only when a shipped gate reads the claimed fact” rule.

2. **P1 — Mapper semantics claim is not read from the mapper bytes.**  
   `NAMED.md:1497` claims:  
   `mapper FUN_00507410 (17 insns, 203 call sites): byte = id/8 truncating toward zero, mask = 1<<(id&7)`  
   The only relevant gates are `G9` and `G13` in `scripts/m349_unit_id.py:305-307` and `:337-340`. `G9` only checks that a hardcoded window `MAPPER..MAPPER+0x26` contains 17 parsed rows and that exact-text `call 0x507410` occurs more than 150 times. It does not parse the mapper’s arithmetic, does not verify 203 call sites, and does not verify the function boundary. `G13` checks a Python model `byte_bit()` against hardcoded expected tuples; it never reads `FUN_00507410`’s instructions. Mutants `MU11` and `MU12` mutate the Python model, not real parsed instructions. Therefore the claim “byte = id/8 truncating toward zero, mask = 1<<(id&7)” is not gated from the binary. If the mapper’s real instruction sequence changed while preserving length/call count, the gate would stay green.

3. **P1 — Cost-table claim overstates what `G8` verifies.**  
   `NAMED.md:1496` claims:  
   `a unit type costs [0x984d44+48*type] = the 72-record array 0x984d38 stride 0x30 +0xc`  
   `G8` at `scripts/m349_unit_id.py:302-304` checks only:
   - parsed `cost_stride == 48` from `lea`/`shl`,
   - hardcoded `cost_base - arr_base == 0xC`,
   - exact instruction `imul edi,DWORD PTR [edx+0x984d44]`.

   It does not parse `0x984d38`, does not parse stride `0x30`, and does not verify “72-record”. The printed line at `scripts/m349_unit_id.py:275-276` is also misleading: it prints `arr=12*0x30+0xc` from `cost_base - arr_base`, not a measured 72-record array. The mutant `MU4` only mutates the Python stride calculation, not the claimed array base/stride/record count. The claim as written is not actually verified.

4. **P2 — Facility-leg claim says “gated by bit 2”, but the pinned code only shows bit 2 being set.**  
   `NAMED.md:1495` claims:  
   `id>=64 gated by bit 2 of the item word @0x98adb8`  
   The evidence and gate pin only these instructions (`scripts/m349_unit_id.py:105-111`, `evidence/m349_unit_id.txt:24-29`):
   ```text
   cmp ebx,0x40
   jl 0x4efed1
   mov ax,WORD PTR [edx+0x98adb8]
   or al,0x4
   mov DWORD PTR [ebp-0x20],0x0
   ```
   This shows the `>=0x40` path OR-ing bit 2 into the word, not testing/gating on bit 2. The gate `G2` only checks this exact instruction list. If the real behavior is “set bit 2” rather than “gated by bit 2”, the prose is wrong; if the real behavior is gating, the instrument does not read the gate/test/store sequence needed to prove it.

6. **P2 — B31 claim names specific heads, but `G10` only checks class counts.**  
   `NAMED.md:1499` claims:  
   `B31's 6 recorded heads = 4 unit types (2,8,3,6) + 1 facility (2) + 1 >=64 (321)`  
   `G10` at `scripts/m349_unit_id.py:310-311` only asserts:
   ```python
   counts == {"UNIT": 4, "FACILITY": 1, "BIGITEM": 1, "SENTINEL": 0}
   ```
   It does not assert the actual heads `2,8,3,6,2,321` or that the facility head is `2`. If the B31 oracle changed to different heads with the same class counts, the gate would remain green. The specific-head claim is therefore not gated.

7. **P2 — Rival claim “-(design-192) predicts -4 vs recorded -6” is not tied to recorded bytes in the gate.**  
   `NAMED.md:1500` claims the rival is dead because it predicts `-4` versus recorded `-6`. In `scripts/m349_unit_id.py:321-323`, `r2` is hardcoded arithmetic:
   ```python
   r2 = (-(195 - 192), -(196 - 192))
   ```
   `G11` at `:329-330` checks `r2[1] == -4 and r2[1] != -6`, but the recorded `-6` is not read from `evidence/b31_facoracle.txt` in that gate. `b31_heads()` is used only for class counts in `G10`. The printed rival line says “recorded (-3,-6)”, but the gate does not verify that the recorded trace actually contains `-6`. This makes the rival refutation partly tautological.

8. **P2 — `G9` does not verify the claimed 203 call sites.**  
   `NAMED.md:1497` and `evidence/m349_unit_id.txt:77` claim `call_sites=203`. The gate at `scripts/m349_unit_id.py:305-307` only requires `len(mapper_calls) > 150`. A binary/listing with 151 call sites would pass. If the claim is “203 call sites”, the gate should assert equality or at least the exact measured number; otherwise the claim should be weakened to “more than 150”.

10. **P2 — “ONE per-player bitmap” is only half-verified: base/stride are parsed, player indexing is not.**  
   `NAMED.md:1498` claims `0x95da9c+304*player`. `G7` at `scripts/m349_unit_id.py:299-301` verifies the base `0x95da9c` and computed stride `304` from two sites. But `stride_304()` at `:181-195` merely parses `esi`-based `lea`/`shl` arithmetic; it does not verify that `esi` is the player index or that the two sites are in per-player contexts. The claim “per-player” is therefore broader than the instrument’s measured fact. It should either be narrowed to “same base and stride at both sites” or the instrument should parse/verify the player-index source.
