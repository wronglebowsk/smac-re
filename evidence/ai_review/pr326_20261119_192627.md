## Findings

1. **P1 — “sole carrier” is measured only over immediate‑dest `fread` legs, but claimed as a whole‑loader fact**  
   `scripts/m324_save_carry.py:95-99`, `scripts/m324_save_carry.py:124-127`, `NAMED.md:1286`  
   `COV` and `IMG_ROUND` only consider `R` legs whose `dest` is an immediate and whose `size` is known. `covers()` returns false for `dest is None` / `size is None`, and T1 shows several real legs with `dest=reg/heap` or `size=?`. The script’s header calls this a declared resolver limit, but the NAMED row says simply “ROUND=blob+44 YEAR=+48; sole carrier”, and G2’s `img-wide=['0x59688a']` only proves no *immediate‑dest static read leg* covers ROUND. If the save data is read into heap and then copied/restored into `0x985afc`, G2 cannot see it. As written, the claim is broader than the instrument’s window; either qualify the claim to “immediate‑dest direct carrier” or add a measurement/proof excluding heap/reg restoration paths.

2. **P1 — M324 mutate digest hashes labels/gate sets, not mutation measurements**  
   `scripts/m324_mutate.py:99-103`, `evidence/m324_mutate.txt:20-21`, `NAMED.md:1292`  
   The digest is computed from `(mid, kind, declared, observed, verdict)` only: `mid`, mutant kind, expected/observed gate names, and OK/NO‑OP. It does not hash any measured literal, instruction bytes, save bytes, file facts, legs, coverage, writer set, closure size, or evidence values. This is exactly the kind of digest defect called out in the prior review round: a digest that can stay identical even if a mutant’s measured payload changes, as long as the same gate labels fail. For M324, the acceptance instrument hashes rich measured detail; the mutation harness does not. The harness digest `f8e16fde85c1ea18` is therefore not a stable digest of the mutation evidence. Hash each mutant’s actual measured delta, or at least the measured fact the mutant rewrites, plus the gate details.

3. **P2 — G2/G8 use “first call-site” where the claim is execution order / header-first, but the metric is merely address-minimum among legs**  
   `scripts/m324_save_carry.py:192`, `scripts/m324_save_carry.py:310-312`, `scripts/m324_save_carry.py:345-346`, `evidence/m324_save_carry.txt:80`, `NAMED.md:1290`  
   `FIRST_WRAP = min(l[0] for l in LEGS)` is just the lowest codec wrapper call address. The prose claims “header first” and uses it to kill R1. A linear min over discovered legs does not establish the first executed save-carry read/write leg: earlier branches may be dead, the codec has diamonds, and legs can be conditionally executed. If any earlier discovered wrapper is conditional/unreachable but numerically lower, the gate is measuring source order, not runtime order. Either pin the actual codec execution chain from function entry to the header leg or rename the claim to “lowest discovered codec wrapper call-site”, and ensure G8 does not treat that as an execution-order proof.

4. **P2 — R2 “rebuild dead” relies on one instruction at `0x5a108b` but does not verify the const‑0 value source**  
   `scripts/m324_save_carry.py:339-342`, `evidence/m324_save_carry.txt:91`, `NAMED.md:1291`  
   R2 uses:
   ```python
   INS.get(0x5a108b) == ("mov", "DWORD PTR ds:0x985afc,esi")
   ```
   to support “its store is const-0 via esi (M323)”. That checks only that some register named `esi` writes ROUND. It does not check that `esi` is zero at that point, nor that `0x5a0fa0` is not called before that store, nor that the function at `0x5a0fa0` has a const‑0 initializer path. MU17 reddens G8 by changing `esi` to `edx`, but a real mutation could change the `esi` setup to `mov esi, 1` while keeping the checked store byte-identical and G8 would remain green. The prose “re-derive/rebuild dead” needs a stronger measurement: pin the def site(s) for `esi` and its constant, or explicitly limit the claim to “no direct-call closure writer and no M323-known `mov esi` shape seen”.

5. **P2 — G7 claims mode=0 but only pins xor/jne/no‑ebx‑defs; it does not pin that mode is used/passed or that the xor belongs to the codec call argument**  
   `scripts/m324_save_carry.py:197-204`, `scripts/m324_save_carry.py:210-217`, `evidence/m324_save_carry.txt:88`, `NAMED.md:1290`  
   The row says “mode=0” and G7 checks:
   ```python
   0x597efb: xor ebx,ebx
   0x597f05: jne 0x597f12
   EBX_DEFS_BODY == []
   ```
   but does not verify that `ebx` is actually the mode argument to `FUN_00596850`, does not pin the push of `ebx` if mode is passed that way, and does not inspect the codec’s mode dispatch. If the real mode flag is a different register/global, these pins prove only that `ebx` is untouched in that small body. Since the row is marked VERIFIED and MU12/MU13 only touch `CPINS`, not the mode argument path, the mode claim is weakly measured.

6. **P2 — G4 verifies the `g999fa4` “MAX-gated fold” pins but does not prove MAX-gating from the printed control flow**  
   `scripts/m324_save_carry.py:151-169`, `scripts/m324_save_carry.py:275-280`, `evidence/m324_save_carry.txt:85`, `NAMED.md:1289`  
   The claim says “fold `[this+a24]*20bc+[94d650]` MAX-gated”. G4 pins eight instructions including `cmp`/`jle` and writes to `0x999fa4`, but it does not verify the comparison/branch actually implements MAX rather than MIN or an unrelated guard. A mutation could flip `jle` to `jge`? Wait MU14 changes target, not condition. If condition code is changed to `jge`, `pin_ok(FOLD)` fails because it expects exact `jle`, so the harness catches that exact literal. But the *semantic* claim “MAX-gated” still relies on interpreting signed/unsigned `jle` with operands `[ecx+0x94d650]` and current `edx`; no gate verifies operand ordering/signedness or that the selected value is maximum. At minimum, the NAMED row should say “`cmp`/`jle` control shape pinned as MAX-gated” or add measurement pinning the branch target/store skip relationship explicitly.

7. **P2 — `4e0350 callers {514ecf,517e3a}` are pinned as image-wide call sites, but “absent” from closure only excludes direct call closure**  
   `scripts/m324_save_carry.py:171-181`, `scripts/m324_save_carry.py:283-289`, `evidence/m324_save_carry.txt:79,87`, `NAMED.md:1290`  
   G6 computes:
   ```python
   YR_CALLERS = calls to 0x4e0350
   WR_IN_CLOSURE = CLOSURE & RWRITERS
   0x512b40 not in CLOSURE
   0x516b80 not in CLOSURE
   ```
   and the row says callers “absent”. But `CLOSURE` only follows direct `imm32` calls through owner functions. If either pump is reached by an indirect call, jump table, callback, or data pointer, it can remain “absent” while still being executable during load. The script declares direct-call closure limits, but the table wording (“loader closure 440, 0 writers; callers absent”) sounds stronger. Either qualify the claim to direct-call closure or add a measurement of the pump call graph entry points used by the loader.

8. **P2 — `M272_WFAM` checks only the presence of writer function PCs in the gdblog, not writer events or return values**  
   `scripts/m324_save_carry.py:219-230`, `evidence/m324_save_carry.txt:80,88`, `NAMED.md:1290`  
   `M272_WFAM` filters top-level keys `pc` in a tuple of writer function addresses. It does not check whether any of those pcs are return points, whether the observed `round` changed, or whether those addresses are actually writers in the disassembly. G7/R2 use it as “writer-fam events=0”. The M272 log may have been produced by a limited set of breakpoints; absence of those exact pc keys is not a proof of no writer events unless the instrumentation covered all writer instructions. If this is relying on M323’s prior writer census, cite that census as part of the evidence; otherwise the “0 writer-fam events” fact is under-gated.

9. **P2 — Acceptance digest includes unprinted or non-reproducible detail; rerun stability is claimed but the digest detail is not self-contained**  
   `scripts/m324_save_carry.py:357-362`, `evidence/m324_save_carry.txt:92`, `evidence/m324_save_carry_rerun.txt:92`  
   The digest is computed from:
   ```python
   detail = "\n".join(GATE lines)
   detail += "\nlegs=%s\ncov=%s\nimg=%s\nfile=%s\nsha=%s\ng999w=%s\nclosure=%d\nm272=%s" % (...)
   ```
   but the printed evidence does not print the exact `detail` string or all digest inputs in a parseable, canonical form. T1 prints legs without file pointers, while digest includes full `LEGS` tuples with `fp`; T6 prints `m272 opener/fac/wfam`, while digest includes the entire `M272` dict. A reader cannot independently reproduce `2cc5fd43ef7ac29f` from the evidence, and any non-deterministic dict ordering/formatting change could alter the digest without altering the visible facts. The instrument should print a compact canonical digest input, or print the hashed summary fields verbatim.
