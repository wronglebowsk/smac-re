## Findings

1. **P1 — `NAMED.md:772` (M303 stub): the archive hash/size are not produced by any shipped instrument.**  
   The stub claims the rotated M303 block is “VERBATIM … (sha1 `e4c1833079918bcc`, 3851 B)”. The diff adds `docs/named-archive-m372-rows.md`, but no gate or script in the PR computes/prints that SHA-1 or byte length. Under the repo convention, a digest/hash cited as verified must be computed and printed by the instrument that verifies it. As written, the integrity claim is decorative: a future edit to the archive could silently break “verbatim” while the stub still asserts the same hash. The textual movement itself looks faithful line-for-line, but the hash/size claim is not gated.

2. **P1 — `NAMED.md:1010` / `scripts/m372_semaphore_cell.py:213-231`: G1 evidence does not cover the whole VERIFIED row.**  
   The row says: “8 refs text==byte; 5 STORE/3 READ; **4 stores `x&0x1800000`, 0 shifts**” and cites only `evidence/m372_semaphore_cell.txt:7-18`, which is G1. The mask and shift facts are measured in G4 (`:47-54`). G1 does not read masks or shifts. The row names `MU11`, which is a G4 mutant, but the cited evidence does not include the G4 output. This violates the “claim marked V only when cited gate reads the claimed fact” rule. Either split the row or cite G4 as well.

3. **P1 — `scripts/m372_semaphore_cell.py:543-556` / `NAMED.md:1014`: G5 does not verify “never a UI label”.**  
   The claim is: “`Semaphore` = 2 image strings, both the INI KEY; **never a UI label**”. G5 only scans a hardcoded VA range `0x690000..0x6A0000`, finds exact C strings, and checks that each is pushed by the loader/writeback owners. It does **not** scan the whole image for references to those string addresses, nor does it check data pointers, UI dialog tables, or non-`push` uses. The negative claim “never a UI label” is therefore not read from the bytes. A UI reference that loads the string address into a register or appears in a dialog table would leave G5 green.

4. **P1 — `scripts/m372_semaphore_cell.py:543-547`: “image occurrences” is measured over a hidden 64 KiB window, not the image.**  
   The evidence line says “image occurrences of `Semaphore`: 2”, and the NAMED row repeats “2 image strings”. The instrument only scans `range(0x690000, 0x6A0000)`. That is a source-only/windowed comparison, not an image-wide census. If the string appeared outside that range, the gate would still report 2. The measurement definition does not match the prose claim.

5. **P2 — `scripts/m372_semaphore_cell.py:360-399` / `NAMED.md:1012`: G3 does not gate the “5 base-2 / 6 base-16” counts.**  
   The claim says parse helpers are “5 base-2 / 6 base-16”. G3 computes `kinds`, prints the counts, and gates only:
   - the `Semaphore` cell uses `0x5ea493`,
   - parser charset/shift properties,
   - `kinds.get(0x5ea484, 0) >= 1`,
   - round-trip exactness.  
   It never asserts `kinds[0x5ea493] == 5` or `kinds[0x5ea484] == 6`. A real input mutation that changed one base-2 cell to base-16, while leaving the `Semaphore` cell and round-trip intact, would keep G3 green despite the claimed census being false. No named mutant reddens the count claim.

6. **P2 — `scripts/m372_semaphore_cell.py:561-590` / `NAMED.md:1015`: G6 does not verify “all new-game”.**  
   The claim says bit23/bit24 readers are at specific sites and “all new-game”. G6 only checks the exact reader tuples:
   ```python
   tuple(found[0x800000]) == PINS["bit23_readers"]
   tuple(found[0x1000000]) == PINS["bit24_readers"]
   ```
   It does not resolve those sites to functions, does not check function names/properties, and does not verify “game-start / new-game”. The “all new-game” part is prose unsupported by the gate.

7. **P2 — `scripts/m372_semaphore_cell.py:561-583`: G6’s definition of “read” is narrower than the claim.**  
   The claim says bits are “read” at those sites. The scanner only recognizes:
   - `test`/`and` with the exact immediate and a direct `ds:0x985ae8` operand, or
   - `test`/`and` with the immediate where the first operand register was most recently loaded from `ds:0x985ae8` within 30 instructions.  
   It does not recognize `bt`, `shr`+mask, `cmp` against a masked value, or other bit-test idioms. If a real reader used another idiom, G6 would miss it while still claiming a complete occupant census.

8. **P2 — `scripts/m372_semaphore_cell.py:593-632`: G7’s “address dwords image-wide” scan is unaligned and includes non-mapped file bytes.**  
   The gap claim says “0 address dwords image-wide”. The instrument does:
   ```python
   pos = exe.find(pat)
   while pos >= 0:
       gap_dw.append(...)
       pos = exe.find(pat, pos + 1)
   ```
   This searches every byte offset in the raw PE file, not aligned dword locations in mapped image sections. It can count unaligned byte sequences or file padding as “address dwords”. The positive controls are also raw-file counts, not mapped-image pointer counts. The measurement does not cleanly match the claim.

9. **P2 — `scripts/m372_mutate.py:99-103`: mutation coverage reporting is wrong.**  
   The harness prints “coverage (gate -> mutants that redden it)”, but computes:
   ```python
   cov = {g: [r[0] for r in rows if r[2] == g and r[5]] for g in GATES}
   ```
   That lists only mutants whose **expected** gate is `g`, not all mutants that actually reddened `g`. The evidence itself shows cross-gate reddening: `MU2` reddens `G2,G5`, `MU4` reddens `G4,G6`, `MU7` reddens `G1,G3`, but the coverage table omits those. This is not merely cosmetic: the harness’s advertised coverage audit is inaccurate, and a future maintainer could rely on the printed coverage map when deciding whether a gate is independently reddened.

10. **P2 — `scripts/m372_mutate.py:43-53`: the ENV mutant can silently use a stale truncated cache.**  
    `truncated_cache()` writes `m372_notloader.txt` to the system temp directory and returns it if it already exists:
    ```python
    if os.path.exists(dst):
        return dst
    ```
    It does not verify that the existing file was generated from the current `scratch/m574/text.txt`, nor does it remove it after use. If the cache changes, or if a stale/corrupted temp file remains, `A7` may test the wrong input while still appearing to kill `G0`. This undermines the ENV mutant’s reproducibility.
