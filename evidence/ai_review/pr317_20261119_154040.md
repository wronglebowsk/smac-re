P2 — `scripts/m319_guard_hoist.py:122-130` + `NAMED.md:M319 G1/re-derived partition`  
`pair_at()` claims to identify the refresh pair:

```python
d1 = next(... tgt_of(b) == REFRESH[0] ...)
...
d2 = next(... tgt_of(b) == REFRESH[1] ...)
return None if d2 is None else (d1, d2)
```

but it does not enforce that `0x4e8d60` precedes `0x4e78e0`.  It only finds some first-callee target and some second-callee target independently in the next 6 instructions within `PAIR_REACH`. P2 — `scripts/m319_guard_hoist.py:326-356` + `NAMED.md:M319 row “NO MEMO-GATED ARRIVAL”`  
The classifier only searches for `cmp/test` instructions as flag setters:

```python
for a in order[i0:i1]:
    if ins[a][0] in ("cmp", "test"):
        fs = a
```

then classifies only those.  On x86, an arrival conditional jump can be gated by an intervening flag-setting ALU instruction, e.g. `add`, `or`, `sub`, `dec`, `xor`, including one that consumes a register containing the memo value or a live copy of it.  Those are excluded from the “memo-test” analysis and recorded as `none` or indirectly as `other-test`.  Therefore the stronger prose claim “NO MEMO-GATED ARRIVAL” is not read from all possible flag setters.  At minimum the instrument should either:

1. find the last instruction that writes the relevant status flags, not merely the last `cmp/test`; or  
2. downgrade the prose to “no memo compare was visible to the shipped cmp/test classifier.”

This matters because G6/G7 can stay green while the instrument is blind to a non-`cmp/test` memo gate.

P2 — `scripts/m319_guard_hoist.py:187-202` + `evidence/m319_guard_hoist.txt:12-15` + NAMED row “4/12 guarded / 8/12 unguarded”  
The guard re-derivation is advertised as independent, but `guarded()` computes `live_copy(b, BB4)` relative to the jump `b`, then accepts an earlier `cmp` if any of that `cmp`’s registers are live-copy registers at `b`:

```python
cp = live_copy(b, BB4)
if cp and any(E.reg_norm(p) in cp for p in parts):
    return (b, t, "via-copy", c)
```

That is not sufficient to prove the `cmp` compared the memo copy.  A false positive is possible with a sequence like:

```asm
cmp eax, esi
mov eax, ds:0x68cbb4
je  skip_store
store
```

Here `eax` is a live memo copy at the `je`, but the preceding `cmp` did not compare the memo.  The current real-image result may be correct, but the gate’s “INDEPENDENT guard rule” is not sound.  It needs to track liveness/copy status at the `cmp`, or at least forbid copy-derived acceptance unless the register was loaded from the memo before that `cmp` and not overwritten before it.  Otherwise G1 can certify a guard partition based on an unrelated old compare.

P2 — `scripts/m319_guard_hoist.py:233-238` + `NAMED.md:M319 “MEMO READS FEW + PRIVATE”`  
The claim is “exactly 6 read/test instructions image-wide.”  The instrument computes refs by substring on operands and excluding only its own `is_store()` pattern:

```python
def is_ref(mn, ops):
    return "0x68cbb4" in ops.strip() and not is_store(mn, ops)
```

`is_store()` only recognizes `mov [DWORD PTR ]ds:0x68cbb4, ...`.  Any other store-like instruction that writes the memo and contains the address, such as `or`, `add`, `and`, `lea`, or a differently formatted store, would be counted as a read/test.  Conversely, a true non-`mov` read that does not contain the exact literal due to parse normalization could be missed.  The gate pins the current six addresses, so it is stable on this image, but the prose “read/test instruction census” depends on an under-specified instruction class.  The gate/evidence should state that this is an operand-substring census under the shipped parser, or the classifier should explicitly distinguish reads, tests, and other memo-touching writes.
