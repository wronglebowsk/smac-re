P1 — `scripts/m357_pref_bits.py:470-471` (`gate("G6c", True, ...)`)  
**A shipped gate is hard-wired green.** `G6c` is the “bit -> label (the answer)” gate, but its predicate is literally `True`. It cannot fail on any input, so the printed `[PASS] G6c` is decoration. This violates the mutation rule directly: a gate that stays green under its own harness is not evidence. It matters because the milestone’s headline answer is the bit-to-label table; the instrument claims 23/23 gates, but one of those gates is not a gate.

P1 — `scripts/m357_pref_bits.py:305-307` (`gate("G4c", len(extra) == len(rb - ui), ...)`)  
**The “4 rebuild ids have no UI row” gate is tautological.** `extra` is defined as `sorted(rb - ui)` immediately above, so `len(extra) == len(rb - ui)` is always true. The gate cannot fail even if the printed extra-id list is empty, wrong, or if `rb - ui` changes. The NAMED row at `NAMED.md:1565` cites `:183-186` for this claim, but line 186 is this vacuous gate. It matters because the claim “0x37/0x38/0x39/0x50 have no row” is only printed, not asserted.

P1 — `scripts/m357_pref_bits.py:497-502` (`gate("G7a", ... == ... or ... <= ...`)  
**The Laptop-delta gate accepts a subset, not the claimed exact delta.** The prose claim is that `Laptop!=0` clears exactly `A{7,27,28}/B{19}`. The gate passes if the cleared set is equal to that set **or** merely a subset of it. An empty cleared set, or a missing one of the four bits, still passes. The NAMED row at `NAMED.md:1567` cites `:347-353` and names `MU5,MU15`, but the shipped mutants do not redden `G7a`; they target the Tutorial-label gate. So the delta claim is not falsified by its own harness.

P1 — `scripts/m357_pref_bits.py:288-291` (`BY_ID = {r["id"]: r ...}`) and `:300-303` (`G4a`)  
**The rebuild-table claim “70 ids -> exactly one (field,bit)” is not gated for uniqueness.** `BY_ID` silently collapses duplicate ids by overwriting the earlier entry. `G4a` only checks that each decoded row has a truthy `field` and `bit`; it never asserts `len(REBUILD_ROWS) == len(BY_ID)` or that no id maps to multiple encodings. Also, `bits(r["bit"])[0]` hides multi-bit OR immediates by printing only the lowest set bit. A mutation that made one id encode two bits, or duplicated an id with a different field/bit, could survive the cited gates. This matters because the row-to-bit injectivity claim depends on the rebuild table being a clean id -> single-bit map.

P2 — `scripts/m357_pref_bits.py:132-168` (`build_pages`) and `NAMED.md:1562`  
**The “read section by name -> next-line -> strcpy into slot -> add_item(text,id)” claim is only partially read.** The instrument locates a `push <name_va>` followed by `call 0x5ea431`, counts `call 0x5ea448`, and near each `call 0x604fd2` picks the nearest non-`TEXTBUF` push as `id` and the nearest push in `0x68b600..0x68b7ff` as `slot`. It never verifies:
- that the pushed name VA actually contains the expected section string;
- that the text line is copied into that slot (`strcpy`/destination dataflow);
- that the chosen `id` is the `add_item` id argument rather than some other nearby immediate;
- that the nth row corresponds to the nth `Script.txt` line.

`G1a` only checks non-null slot/id; `G2a` checks consecutive slot VAs; `G3b` checks counts. The prose claim is about the whole instruction/dataflow, but the gates mostly measure source-side counts and positional assumptions.

P2 — `scripts/m357_pref_bits.py:417-429` (`G7d`)  
**The default-mask derivation gate uses a cross-product, not the actual `and`/`add` pairing.** It collects all `and esi,imm` and all `add esi,imm` in the loader window, then computes every `and + add` combination and checks that the two expected `Laptop!=0` words appear somewhere in that cross-product. It does not verify which `and` pairs with which `add`, nor does it assert the `and` immediates. With two `and`s and two `adds`, wrong pairings can still produce the expected values by accident. The claim that the `Laptop!=0` words are derived by the loader’s `and`+`add` is therefore weaker than the prose suggests.

P2 — `scripts/m357_pref_bits.py:313-345` (`apply_dataflow`)  
**The APPLY simulation does not model OR-to-cell stores.** The symbolic tracker records a cell only for `mov ds:0x..., reg`. For `or` instructions, if the destination is a cell (`ds:0x...`) rather than a register or `[esi+...]`, the code falls through and records nothing. The M355/M357 prose talks about APPLY ORs feeding `0x92befc`/`0x92bf00`; if the real endpoint were an OR directly into the cell, `G5c/G5d` could miss it. The current evidence happens to show final `mov` stores, but the instrument’s definition of “APPLY dataflow” is narrower than the claim.

P2 — `scripts/m357_named_rotate.py:54-67` (`rotate()`)  
**The rotation script is not actually idempotent, despite the docstring.** After rotation, `NAMED.md` contains headings like `## M272 (STUB ...`. `TARGETS` still contains `"## M272 "`, so a second run’s `block_of()` can match the stub, treat the stub as the settled block, rewrite the archive with the stub, and destroy the byte-exact archived block. The `rotate()` function has a guard for both stubs present, but `--verify` and the general docstring claim idempotence; the failure mode is archive corruption if the guard is bypassed or if only one stub is present. This matters because the archive is the evidence for the rotated M272/M273 blocks.
