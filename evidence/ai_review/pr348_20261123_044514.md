P1 — `scripts/m333_feeder_slot_census.py:318-329` / `NAMED.md` M333 G6 row: the “0 stores image-wide” claim is not actually measured image-wide, and not even all .text stores.

What is wrong:
- The G6 store census only looks for direct absolute stores whose first operand has displacement `0x985ba0`:
  ```python
  d = memref(parts[0])
  dd = ...
  if dd == SEL_BASE and INS[a][0] in m326.STORE_MN:
      wsel.append(a)
  ```
- It does not detect pointer stores, e.g. `lea eax,[0x985ba0]` / `mov [eax], ...`, nor stores through a computed address that resolves to `0x985ba0`.
- The scan is over the `.text` instruction cache, but the printed row and NAMED claim say “image-wide”:
  ```text
  G6 0x985ba0 image-wide: stores=0 ...
  ```
  while the gate text says “READ-ONLY in .text (2 loads, 0 stores image-wide; writer outside .text)”.

Why it matters:
- The VERIFIED claim is stronger than the measurement. A real .text pointer-store writer would leave the gate green while falsifying “READ-ONLY” and “writer outside .text”.
- This is exactly the kind of hidden source-only / direct-disp-only comparison the repo laws warn about. The gate can pass on a false claim.

P1 — `scripts/m333_feeder_slot_census.py:347-356` / `NAMED.md` M333 G7 row: the “table is 39 rows (`0x750`=1872=39*48 read out of .text)” claim is mostly hardcoded arithmetic, not a byte-read measurement.

What is wrong:
- The instrument only checks that the literal `0x750` appears somewhere in `.text`:
  ```python
  row1872 = [a for a in ADDRS if re.search(r"\b0x750\b", INS[a][1])]
  ```
- It then asserts constants:
  ```python
  1872 // ROW == TABLE_ROWS
  1872 % ROW == 0
  0x27 == TABLE_ROWS
  never == [0] + list(range(35, TABLE_ROWS))
  ```
  where `1872`, `TABLE_ROWS`, `0x27`, and the charged/never ranges are Python constants.
- It does not read `0x750` as a value, does not verify that it is the table size, does not verify the table bounds, and does not derive `39` from the bytes.

Why it matters:
- The prose says the row count is “read out of .text”, but the gate mostly verifies the instrument’s own constants.
- A wrong table-size interpretation could remain green as long as some unrelated `0x750` exists. The only real byte-dependence is the presence of the literal and `rowdiff`, not the claimed table extent.

P1 — `scripts/m333_feeder_slot_census.py:116-139` / `NAMED.md` M333 G1/G2 fold claim: the shape-pin does not prove the folded register is the register used by the item-table read.

What is wrong:
- `fold48()` scans backward from the read and checks for:
  ```asm
  lea r,[i+i*2]
  shl r,0x4
  ```
  and returns `i`.
- It never checks that the memory operand being read actually uses `r` as its base/index.
- The read is found by displacement only:
  ```python
  reads = reads_at(p1, ITEM_UPKEEP)
  fold = [(a, fold48(a)) for a, op in reads]
  ```
  but `op` is not used to tie the read’s address register to the `shl` destination.

Why it matters:
- The claim is that the item-table read is folded from `esi` by `48*item`. The instrument can pass if the fold computes `esi -> eax` while the table read uses some unrelated register.
- This is a correctness bug in the classifier, not just fragility: the measured shape is not connected to the measured read.

What is wrong:
