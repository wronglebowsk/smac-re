## Findings (most important first)

1. **P1 — `scripts/review_lint.py:56-77`**  
   The digest check (`L3`) is weaker than the stated law/prompt. It merely verifies that a 16-hex string appearing anywhere in the NAMED block also appears somewhere in **any** evidence file cited by the block. It does not verify that the digest is attached to the relevant instrument/harness, printed by that instrument, or computed from the bytes being claimed. A block can cite `evidence/foo.txt` and satisfy `L3` if the digest is in an unrelated tail line, while the actual milestone digest is missing, stale, or hand-copied. Since the digest class is exactly one of the known Greptile findings (`F8 digest not computed/printed by instrument`), this “mechanical layer” cannot close the gap it claims to close.

2. **P1 — `scripts/review_lint.py:62`**  
   The `ACCEPT`/`REVIEW` exemption for `L1` is keyed only on the claim cell beginning with the literal strings `ACCEPT` or `REVIEW`. A real VERIFIED factual claim whose cell happens to start with those words will silently skip the mutant-citation check. Conversely, a non-meta row can be written as `ACCEPT: ...` to bypass `L1`. This is a false-green path in the new gate. If the exemption is intentional, it needs an explicit meta-row convention or table column, not a prefix match.

3. **P1 — `scripts/review_lint.py:79-82`**  
   `L2` only checks that a cited mutant string exists somewhere in `scripts/<id>_mutate.py`. It does not establish that the cited mutant reddens the gate for the claim row that cites it. Under the repo law, “a VERIFIED row names the mutant that reddens it” is a row-to-mutant-to-gate relationship, but this lint accepts a row that cites an unrelated existing mutant. That makes the mechanical layer a naming/citation check, not a coverage check, while `docs/AI-REVIEW.md` presents it as closing the “no mutant = decoration” defect class.

4. **P2 — `scripts/ai_review.py:80-84`**  
   The script treats any non-empty `content` as a successful review. It does not inspect `finish_reason`, compare `usage.completion_tokens` to `max_tokens`, or warn if output is truncated. The replay evidence explicitly identifies 8192-token truncation as a real failure mode (`docs/AI-REVIEW.md` scoreboard, `evidence/ai_review_replay/run.log`, `qwen36_m317.json`, `strata_m317.json`). Production sets `16384` but still cannot detect hitting that cap. A truncated review may be posted and counted as “review produced” while missing later findings, undermining the semantic half of the pipeline.

5. **P2 — `docs/AI-REVIEW.md:38-45` + `scripts/ai_review.py:50-58`**  
   The docs claim “no endpoint committed — gate law,” but `ai_review.py` resolves the endpoint from `~/.hermes/config.yaml` while committing only the provider key name and model alias. The endpoint itself is not hardcoded in the production script, but the replay evidence script commits internal endpoints: `evidence/ai_review_replay/replay.py:38` and `:43` contain `http://192.168.1.12:8080/...` and `http://192.168.1.213:8010/...`. If endpoint/hostname secrecy is part of the repo hygiene law, the committed replay harness violates it, even if it is “only evidence.” It also makes the evidence non-portable and tied to a private LAN.

6. **P2 — `evidence/ai_review_replay/replay.py:16` and `48-50`**  
   The replay script assumes `scratch/review_replay/` already exists. It computes `OUT` but never calls `os.makedirs(OUT, exist_ok=True)` before opening output files. The recorded run succeeded because the scratch directory existed, but rerunning after cleanup, on another machine, or in a fresh checkout will crash with `FileNotFoundError`. That weakens the reproducibility claim for the replay experiment.

7. **P2 — `skill/templates/cron-milestone-loop.md:59-60` vs `NEXT_PROMPT.md:134-135` vs `skill/references/session-discipline.md:300-302`**  
   The pipeline copies disagree on the `NEXT_PROMPT.md` size limit. `NEXT_PROMPT.md` says patched by section to `<=12,000 B`; `SKILL.md` also says `<=12,000 BYTES AT CLOSE`; the kickoff template says `<=15,500 chars`; the reference depth says `<=15,300 BYTES AT CLOSE`. This is a real operational defect in a unattended loop: the kickoff template can legitimately produce a file past the documented warn threshold and near the hard gate threshold. Since this PR is moving/standardizing pipeline instructions, these limits should be reconciled in the same change.

8. **P2 — `SESSION_NOTES.md:245-247`**  
   The session note claims an `ai_review` smoke test on #314 was “recorded in `evidence/ai_review/`,” but the PR diff adds no `evidence/ai_review/` file. If the smoke test is part of the acceptance evidence for landing the pipeline, it is missing from the diff. The pipeline now depends on saved raw reviews, so an uncommitted or invisible smoke test should not be cited as an acceptance artifact.

9. **P2 — `scripts/review_lint.py:24` + `scripts/review_lint.py:69-77`**  
   The digest matcher is context-free: any bare 16-hex token in the NAMED block is treated as a digest and must appear in a cited evidence file. This can produce false positives for hex object IDs, padded addresses, or quoted binary strings, and it does not require the digest to be near words like `digest`, `acceptance`, or `harness`. The fixture only tests a clean digest-looking string, so this behavior is not represented by the tests. A narrow, context-anchored digest rule would reduce brittle false failures and make the check match the actual claim class.

10. **P2 — `scripts/review_lint.py:25` + `69`**  
   `EVID_RX = evidence/[\w./-]+` can match evidence directories or incomplete citations, but `main()` reads any matched path if `os.path.exists(fp)` is true. A citation like `evidence/ai_review/` in prose could cause an `IsADirectoryError` or an accidental empty digest scan. The lint should require a concrete file suffix or guard directory paths before opening them. This is a real robustness bug in the new mechanical gate, not just style.
