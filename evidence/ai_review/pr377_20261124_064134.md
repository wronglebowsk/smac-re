Findings, most important first:

1. **P1 — `scripts/m351_type_producer.py:365-372` — `read_recorded()` silently falls back to hardcoded heads, so G12 can pass without reading evidence.**  
   `read_recorded()` parses `evidence/m349_unit_id.txt` only if lines match `head=(-?\d+)`; otherwise it returns the literal `[321, -2, -8, 2, -3, -6]`. G12 then uses those values to declare rivals dead. If the evidence file is missing, renamed, reformatted, or no longer contains the recorded heads, the gate still passes from the fallback. That violates the repo rule that VERIFIED claims must be read from bytes and makes the rival-killing evidence non-falsifiable.

2. **P1 — `scripts/m351_type_producer.py:300-303` — G13’s retraction claim is gated on a prose substring, not on the claimed trace fact.**  
   The NAMED row claims M68’s `195 -> -3` is a stale cell read and cites the trace note “re-sorted between the read and the click.” G13 only checks that the literal string `"re-sorted between the read and the click"` exists somewhere in `evidence/m68_key_run_attempt1.txt`. It does not parse the trace, does not bind the note to the `195`/cell read, and does not verify that the cell is a row counter in the trace. A copied or unrelated sentence would keep the gate green.

3. **P1 — `scripts/m351_type_producer.py:283-287` — G12’s rival logic is partly hardcoded and does not actually compare the rival prediction against recorded evidence.**  
   `r2 = {195: -3, 196: -4}` is hardcoded, and the gate asserts `r2[196] != -6`. It never parses the recorded `195/196 -> -3/-6` mapping from evidence. The printed line says “recorded 195/196 -> -3/-6”, but that is also hardcoded prose. The rival is not killed by measured bytes; it is killed by a literal in the script.

4. **P2 — `scripts/m351_type_producer.py:343-345` — the digest does not bind the measured facts or listing bytes.**  
   The digest is `sha1("|".join(PASS) + "|" + TEXT)`. It fingerprints only gate names and the listing path, not the listing SHA, parsed literals, evidence files, or gate details. The x2 record cites `c23a0d70f80d757e` as acceptance evidence, but that digest would remain unchanged if the listing path stayed the same and the gate names stayed the same even if underlying parsed values changed in ways that did not alter gate names. A digest used as a verification fingerprint should include the listing hash and/or parsed measurements.

5. **P2 — `NAMED.md:1528` — the first M351 row cites evidence lines that do not contain the gates for the claimed item/flag fields.**  
   The row claims `item = row+4 (0x401940)` and `flags = row+8 (0x495480)`, but cites `evidence/m351_type_producer.txt:70-76,101`. Those lines are TABLE 0 prose and G1. The actual field facts are gated by G6 and G7, not G1. The row names `MU10` and `MU11`, which redden G6/G7, but the evidence citation does not point to those gates. This is a citation defect: the VERIFIED row is not backed by the cited lines.

6. **P2 — `NAMED.md:1529` — the row-list claim cites TABLE 0 and G10, but the gated facts are G3/G4/G5/G15.**  
   The row claims section A/B structure, loop bounds, candidate table, flag function values, and owner encoding. The cited lines are `:70-75,78,110`: TABLE 0, TABLE 3, and G10. The gates that actually read those facts are G3, G4, G5, and G15. The named mutants correspond to those gates, but the evidence citation does not. This makes the row look gated by prose tables and the wrong gate.

7. **P2 — `NAMED.md:1530` — the “TYPE ORDINAL” row cites G13, which is unrelated to the type-array claim.**  
   The row claims `i` indexes `0x984d38 + 0x30*i` for name and `0x984d44` for cost, matching M349. The cited evidence line `:113` is G13, the cell-vs-item retraction gate. The relevant gates are G3 and G10. The row names `MU4` and `MU5`, which do redden G3/G10, but the citation points to the wrong gate.

8. **P2 — `NAMED.md:1531` — the chooser-uses-`-i` row cites G13, not G14.**  
   The row claims affordability uses `-i`, queue-slot compare uses `-i`, and section A compares `+item`. The cited line `:114` is G13. The actual gate is G14. The named mutants `MU15` and `MU19` do redden G14, but the evidence citation is wrong.

9. **P2 — `scripts/m351_type_producer.py:216-224` — TABLE 3’s “whole flag space” claim is not actually computed over the whole flag space.**  
   The table says “computed over the whole flag space,” but the instrument only samples four unit flag values (`0x10|0..3`) and two facility flag values (`0x20`, `0xa0`). It does not enumerate the full 8-bit flag space, nor does it prove that `0x496050(item)` cannot return values with bit `0x20` clear for facility rows. The prose overstates the measurement.

10. **P2 — `scripts/m351_mutate.py:151-155` — harness scoring can pass even if a mutant reddens the wrong gate, as long as some gate reddens.**  
   For non-NOOP mutants, the harness records `covered |= set(red)` and only appends a `missed` entry if the expected gate is absent. But the final `ok` condition is `scored >= len(MUTANTS)+len(MODEL)-1 and not missed and not uncovered`. If a mutant reddens an unexpected gate and also reddens the expected gate, it is fine; but if the expected gate is missing, it is marked missed. The real issue is that `scored` counts any non-empty red set, and the printed evidence can show `OFF` while still counting as scored if the expected gate is present? More importantly, the harness does not require each NAMED row’s named mutant to redden the specific gate backing that row; it only requires the declared `want` gate. This weakens the mapping from NAMED rows to mutants when citations are already wrong.
