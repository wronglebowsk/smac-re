1. **P1 — `NAMED.md:1478-1483` / `scripts/m348_pref_cowriters.py:437-455`: the “SOLE writer” claim is not gated and is contradicted by the same milestone.**  
   The M348 row says `FUN_0058e7f0 = SOLE writer: 11 stores, 1/cell`, but the instrument only proves that the loader has 11 declared scalar stores and that each declared store site has some parse call in the preceding window. It does **not** prove sole writer-ship image-wide; indeed T3/T4 immediately measure 32 scalar co-stores and 33 total co-store sites. If “SOLE writer” means “sole loader/initialiser”, the prose does not say that; if it means “sole writer”, the claim is false. This is a VERIFIED claim whose gate does not read the claimed fact.

2. **P1 — `scripts/m348_pref_cowriters.py:565-573`: R2 “loader stores have 0 in-function predecessors, all co-stores do” is decorative.**  
   The printed rival says the loader’s stores have no in-function predecessor while all 33 co-stores do, but the code merely sets `ld_store = {CELL_KEYS[c][3] for c in CELL_KEYS}` and checks `len(ld_store) == 11` and `len(sites) == 33`. This violates the “gate reads the claimed fact / mutation must redden it” rule.

3. **P1 — `scripts/m348_pref_cowriters.py:318-355`: the provenance classifier treats non-writing register uses as redefinitions, so the 31/2 EXTERNAL/SELF split is not trustworthy.**  
   In `provenance()`, any instruction whose first operand is in the tracked alias set and whose opcode is not `mov` or one of the listed ALU ops returns `EXTERNAL` as “register redefined”. That includes `cmp`, `test`, and likely other read-only uses. Example: `mov eax, ds:cell; cmp eax, 0; mov ds:cell, eax` would be classified EXTERNAL even though the stored value is the cell’s own value. The M348 row claims `31 outside-value, 2 self-RMW` as VERIFIED, but the classifier can misclassify real self-RMW sites. This is a correctness bug in the instrument’s argument decoding/classifier.

4. **P2 — `NAMED.md:1478` and `evidence/m348_pref_cowriters.txt:16`: digest citation points to the wrong evidence line and “x2 identical” is not evidenced.**

The evidence file contains one run, not two identical runs. The digest is computed and printed, but the cited line does not contain it and the “x2” claim is unsupported by the shipped evidence.

5. **P2 — `NAMED.md:1478` / `evidence/m348_mutate.txt:20`: harness evidence line is wrong.**  
   The M348 header cites `evidence/m348_mutate.txt:20` for `harness 12/12`, but line 20 is the `MU10` mutant line. The harness result is at lines 29-30 (`MUTANTS: 12/12 killed...` / `RESULT: PASS M348: harness 12/12`). This is a direct evidence/citation defect for a VERIFIED mutation claim.

6. **P2 — `scripts/m348_mutate.py:43-45` + `scripts/m348_pref_cowriters.py:254-277`: MU12 does not mutate the byte-level census it is supposed to kill.**  
   The M348 row claims `byte disp32 scan == text scan; byte-only = 2 sentinels + 4 array bases` and names MU12. MU12 patches only the objdump text cache at `0x57ab57`; `byte_scan()` reads `programs/terran.exe` bytes and is unaffected. The byte-only set check therefore stays green; the harness only reddens the separate text-based `materialised scalar addresses` check. So the byte-level claim is not actually mutation-tested by the named mutant.

7. **P2 — `scripts/m348_pref_cowriters.py:404-408`: “Custom World[0] has exactly one co-writer” is not filtered to stores.**  
   `array_fns` collects every non-loader function with a `ds:` reference to `0x92bf18`, regardless of whether the reference is a load, store, RMW, or comparison. The claim and printed gate say “co-writer”, but the code would count a read-only co-reader as a co-writer. It should filter `k == "STORE"` or otherwise prove the reference is a write.

8. **P2 — `scripts/m348_pref_cowriters.py:381-388`: the writeback “scalar loads” count does not verify loads.**  
   `wb = [(c, a, k) for c, a, k, t in loc if fnof(a)[0] == "FUN_0058f0d0"]` counts all direct `ds:` references in the writeback function, then asserts `len(wb) == 11` as “scalar loads”. It does not filter `k == "LOAD"`. If the writeback contained a store or comparison to a pref cell, it would still be counted as a load. The prose claim is about loads; the gate measures unqualified references.

9. **P2 — `scripts/m348_pref_cowriters.py:288-297`: the parse-feed claim is only a window existence check, not a feed check.**  
   For each cell, the instrument searches from the previous store to the current store for any call to `0x5ea484` or `0x5ea493` and records the last such target. It does not verify that the parse call’s result reaches the store, nor that it is the immediate/unique feeder. The M348 row says each store is “fed by” a parse call; the gate only proves a parse call exists somewhere in the block window.

10. **P2 — `NAMED.md:1033` / `docs/named-archive-m348-rows.md:5`: the M314 archive pointer is off by the fence/blank line.**

The rotation itself appears byte-faithful and the sha1/row-count verifier is reasonable, but the human-facing citation is wrong.
