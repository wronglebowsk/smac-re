P1 — `scripts/m325_block220_census.py:571-580` (`feed_direction()`).

The function only checks the literal shapes at `0x442625` (`cmp edx,[field]`), `0x44262b` (`jle`), and `0x442642` (`mov [g999fa4],edx`), then returns `MIN` unless `M325_ALGO=5`. This is the exact “gate stays green under its own mutation” / “source shape measured but whole semantic claim asserted” defect.

P2 — `scripts/m325_block220_census.py:189-216` (`pop_source`) can create false provenance.

It finds the “most recent `push reg`” before a `pop reg`, but it ignores intervening pushes/pops of other registers. x86 stack pops are LIFO:

```asm
push eax
push ebx
pop  eax
```

Here `pop eax` consumes the `ebx` push, but `pop_source` would return the earlier `push eax`. That can turn an invalid address provenance into `STRIDE`/`BLKCONST` in `base_tag`, affecting `G2`/`G3` provenance counts and writer classification. The script declares “push/pop pairing” as a resolver technique, but this pairing is not sound without modeling intervening stack pushes/pops.

P2 — `scripts/m325_block220_census.py:136-161` (`stack_source`) treats calls as safe for `[ebp+disp]` slot forwarding.

It skips `call` instructions and then continues tracing stores to the same `[ebp+disp]`, except when writing to `ebp` itself. But a call may pass a pointer to that stack slot, or otherwise cause callee code to modify `[ebp+disp]`. The instrument declares “no CFG dataflow proof,” but `G2`/`G3` still use this forward stack-slot trace to declare provenance for measured writer sites. If a proven writer’s address depends on a stack slot whose last linear-looking store was not the actual runtime definition, `base_tag` can overclaim `STRIDE`/`BLKCONST`. The gate can remain green even when a real dataflow def was missed.
