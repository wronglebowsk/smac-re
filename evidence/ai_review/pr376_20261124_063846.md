6. **P2 — `scripts/m352_persist_writeback.py:391-404` — G3’s “cell-backed” classification is window-presence, not value provenance.**  
   For direct write sites, the instrument scans the instruction window since the previous write site for any `ds:0x...` inside the pref block and labels the write `CELL` if any such reference exists:

   ```python
   cells = sorted({int(m, 16) for i in INF
                   if prev < i["a"] <= site
                   for m in re.findall(r"ds:0x([0-9a-f]+)", i["arg"])
                   if cell_span(int(m, 16))})
   ...
   elif cells:
       src = "CELL"
   ```

   It does not trace that the cell feeds the value argument passed to `WritePrivateProfileStringA`. The prose claim is stronger: “12 cell-backed writes” and “the persist writes no cell it never read.” The gate only proves that block-cell references occur in the same straight-line window. A mutation that changes the actual value source while leaving a block-cell reference nearby could keep the gate green.

7. **P2 — `scripts/m352_persist_writeback.py:407-418` — G3 does not actually assert “12 cell-backed writes.”**  
   The gate checks:

   ```python
   measured_keys == WRITE_KEYS

   len(stamp_rows) == 1 and stamp_rows[0][3] == "CONST 0xb"
   ```

   It never checks that exactly 12 write rows are `CELL` or `ARRAY`, nor that the non-stamp rows are all cell-backed. `scalars` is a set of first cell entries, so duplicate or misattributed cells could satisfy `len(scalars) == 11` while the row-level provenance is wrong. The printed message hardcodes “12 cell-backed writes,” but the assertion does not read that fact.

9. **P2 — `scripts/m352_persist_writeback.py:531-548` — G6’s “0 stores image-wide” is narrower than the claim.**  
   The store detector only inspects instructions whose textual argument contains the literal `0x6926ec`, then applies a byte-prefix heuristic:

   ```python
   uses = [i for i in INS if "0x6926ec" in i["arg"].lower()]
   ...
   if op in ("mov", "or", "and", "add", "sub", "xor", "inc", "dec", "not", "xchg") \
           and "ds:0x6926ec" in i["arg"] and i["arg"].split(",")[0].strip() != "0x6926ec":
       if not (by and by[0] in ("a1", "a0", "8b", "8a")):
           stores.append(i)
   ```

   It does not detect stores through a register holding the address, computed addresses, or indirect memory forms that do not contain the literal VA in the disassembly text. The byte scan helps catch literal VA occurrences, but it only proves all literal occurrences are `push 0x6926ec`; it does not prove “0 stores image-wide” in the strong sense. The claim should be narrowed to “no direct moffs store or literal VA use other than pushes,” or the instrument needs a real store/alias analysis.

10. **P2 — `scripts/m352_mutate.py:36-38` — MU10 is not a faithful real-instruction mutation because the instruction text is patched while the original opcode bytes remain.**  
   MU10 uses:

   ```python
   ("MU10", {"M352_PATCH": "0x58f3c0|mov    ds:0x6926ec,eax"}, "G6",
    "an epilogue pop becomes a STORE to ds:0x6926ec (the retraction dies)"),
   ```

   `insns()` replaces only the mnemonic text and keeps the original bytes from the cache. G6’s store detector then uses those original bytes to decide whether the instruction is a load or store. This mutant works only because the original byte prefix happens not to be in the load-exclusion list. It is not a real parsed instruction and can hide byte/text consistency bugs in the classifier. A mutation harness for a parser/classifier should either patch bytes consistently or avoid byte-dependent classification in the mutant path.
