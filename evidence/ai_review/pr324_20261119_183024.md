Findings, most important first.

1. **P1 — NAMED.md:1316 — the “pair IN ORDER ≤25 B after” claim is not what G2 measures.**  
   `scripts/m321_memo_owners.py:262-275` counts memo sites with `calls_after(..., window=48)`, and G2 only asserts that both refresh calls occur and are ordered (`scripts/m321_memo_owners.py:610-613`). The 25-byte window is never measured, and `evidence/m321_memo_owners.txt:18-19` prints only booleans, not distances. So a site whose refresh pair occurs 47 B later would still pass G2 while contradicting the prose.

2. **P1 — scripts/m321_memo_owners.py:250-256 — the refresh-order check uses arbitrary set ordering, not the pinned function order.**  
   `calls_after()` returns a list built over `want`, but the call site passes `set(PAIR)` (`scripts/m321_memo_owners.py:267-268`). T3/G2 then interpret `hits[0]` as the first refresh function and `hits[1]` as the second (`scripts/m321_memo_owners.py:270-272`). The order is therefore dependent on Python set iteration, not on `PAIR = (0x4e8d60, 0x4e78e0)`. That makes the claimed M318 order law non-deterministically measured; MU2/MU8 do not repair this because the instrument can be “checking” the reversed order by accident.

3. **P1 — NAMED.md:1317 — “je skips `call 0x4f41f0`” is not gated to `je`.**  
   The instrument accepts any Jcc: `isje = bool(j) and j[0].startswith("j")` (`scripts/m321_memo_owners.py:311-312`), and G4 only checks `x[3]` (`scripts/m321_memo_owners.py:617-620`). A `jne`, `jle`, etc. placed after the test would still satisfy the gate, but the VERIFIED claim specifically names the skip as a `je` predicate. No mutant reddens the mnemonic, so the exact control-flow direction is decorative.

4. **P1 — NAMED.md:1317 — “+0x78/7c/80 zeroed” is not actually verified.**  
   The field scan only records offsets and the final operand string (`scripts/m321_memo_owners.py:314-320`), then G4 asserts the offset set is `[0x78, 0x7C, 0x80]` (`scripts/m321_memo_owners.py:618-619`). It never verifies that the write is `0`, never verifies the base register is the same record pointer, and never checks operand width. Nonzero writes through an unrelated `[reg+0x78]` would still pass. This is a definition/prose mismatch on a shipped V claim.

5. **P1 — NAMED.md:1315 — “4 memo sites … 2 are the a3 form” is under-read.**  
   G2 counts memo stores and refresh order, but nothing pins the instruction form distribution for the four memo sites. The evidence only prints memo addresses (`evidence/m321_memo_owners.txt:18-19`) and unrelated index/pointer stores (`:9-16`). MU1 proves short-form stores matter globally, but it does not establish “exactly 2 memo sites are a3 form”; the gate can be green with 1, 3, or 4 short-form memo stores.

6. **P2 — NAMED.md:1314 — “7 `0x48f100` calls; PE labels …” is only weakly gated.**  
   G3 checks that at least one nutrient-family label exists in FUN_004ee410, at least one PSYCH label exists in FUN_004f41f0, and the label sets are disjoint (`scripts/m321_memo_owners.py:615-616`). It does not pin the count `7`, does not pin the exact expected label set, and does not pin the emitter address in the output. The evidence happens to print seven FUN_004ee410 emitter rows (`evidence/m321_memo_owners.txt:21-27`) and one FUN_004f41f0 row (`:28`), but the gate does not read those facts.

7. **P2 — NAMED.md:1317 / evidence:69 — “callee re-gates @0x4f43a0” is only “exactly one self-gate exists.”**  
   G6 asserts `len(selfgate) == 1` (`scripts/m321_memo_owners.py:622`). It does not pin the address `0x4f43a0`, the tested register, or the loaded-from offset relationship beyond what is needed to populate `selfgate`. MU12 reddens the current site, but if the instrument later found one different self-gate and missed `0x4f43a0`, G6 would still pass while the cited claim would be false.

8. **P2 — NAMED.md:1318 — “the 52-chain rival dies on the histogram” is not asserted by G1.**  
   G1 checks that there are many 304-chains, that one feeds `ds:0x8f0d60`, and that the fold is 304 (`scripts/m321_memo_owners.py:605-608`). It does not check the histogram contents, specifically the 52-chain count or that the rival multiplier is 52 (`evidence/m321_memo_owners.txt:2`). The printed rival line is produced by a hardcoded comparison `unit_stride != 304` (`scripts/m321_memo_owners.py:240-243`), not by comparing the measured 52-chain histogram against the measured 304-chain evidence.

9. **P2 — scripts/m321_memo_owners.py:193-200 — `back_def()` ignores its declared locality bound.**  
   `back_def()` has a `limit` parameter, but the implementation ignores it and scans all the way back to the function entry (`scripts/m321_memo_owners.py:197-199`). This matters because many V claims rely on “nearest def” (`T3`, `T4`, `T5`, `T5b`, `T6`). The unused limit does not by itself make a listed fact false on the current corpus, but it means the instrument’s advertised “nearest within a bounded window” semantics are not what is enforced; an older far-away definition can silently satisfy gates that the prose implies are local.

10. **P2 — evidence/harness citation hygiene: `m321_mutate.txt` line 15 is not the harness line for `MU4 = declared NO-OP` as cited in the cursor.**  
   The cursor says harness `PASS M321_MUTATE: 13/13` (`SESSION_CURSOR.md:5-7`) and `evidence/m321_mutate.txt:15` for `MU4 = declared NO-OP`. Line 15 is the final PASS line (`evidence/m321_mutate.txt:15`), but MU4’s actual measurement is line 5 (`MU4 redden NOTHING OK`). That is a minor citation defect for a hygiene-governed repo: the evidence line cited for a declared no-op should point to the measured no-op row, not only to the aggregate success line.
