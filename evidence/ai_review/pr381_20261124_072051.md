P2 — `scripts/b33_extract.py:57-66` — the census parser misclassifies memory operands containing hex displacements as direct branch/call targets.

`operand_token()` does:

```python
if mnem.startswith("j") or mnem == "call":
    tgt = re.search(r"\b(0x[0-9a-f]+)\b", operands)
    return tgt.group(1) if tgt else "-"
```

For an indirect call such as `call DWORD PTR [eax+0x4]`, this returns `0x4`. The committed census contains lines like:

```text
4f24d7 call     0x4
4f25b2 call     0x4
```

Those are not direct calls to address `0x4`; they are parser artifacts from displacements inside memory operands. The same bug would misclassify an indirect jump with a displacement as a direct target. This matters because the census is the committed artifact used to build the CFG and to support the “closed CFG” claim. Even if current CFG code ignores call targets, the fixture is wrong and the parser is not safely distinguishing direct control transfers from memory operands.

P2 — `scripts/b33_extract.py:61-65` — the read/write classification marks `cmp` and other non-writing instructions as writes.

The extractor decides write direction by checking whether the `[ebp-...]` token appears in the first operand:

```python
first = operands.split(",")[0]
write = 1 if ebp.group(0) in first else 0
```

That is wrong for `cmp`, `test`, and similar instructions. The committed census already shows the defect, e.g.:

```text
4ef8ff cmp      w[ebp-0x1c]
4f04d4 cmp      w[ebp-0x18]
4f0637 cmp      w[ebp-0x18]
```

This matters because G5 depends on `writes(census)` finding writes to `[ebp-0x30]`. The current function may not contain a `cmp [ebp-0x30], ...`, but the instrument’s “write” notion is not sound. A future dump or decode drift that introduces a comparison against `[ebp-0x30]` would create a false write site, or the current fixture’s direction labels cannot be trusted for the claimed “operands that touch `[ebp-0x..]`” with read/write direction.
