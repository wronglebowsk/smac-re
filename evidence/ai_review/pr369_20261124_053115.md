P1 findings

1. **`scripts/m346_alert_raiser.py:345` / `scripts/m346_mutate.py:46` — MU15 is a fake mutant, not a byte/instruction mutation.**  
   `G16` is written as:
   ```python
   PATCH_ALGO != "drop_drain" and len(first_byte_writers) == 5 ...
   ```
   and `MU15` reddens it only by setting `M346_ALGO=drop_drain`. That directly disables the gate instead of rewriting a measured literal or parsed instruction. The mutation law says a gate that stays green under its own mutation is decoration; here the “mutation” is a hook that forces failure. This makes the `R2 not a queue` claim effectively ungated. Fix: remove the `PATCH_ALGO` condition from the gate and make MU15 mutate real instructions/data so the measured first-byte-writer set changes.

2. **`NAMED.md:1477` — the first M346 VERIFIED row names `MU1-3`, but `G1` has no mutant.**  
   The row claims:
   > after the pop ... posts exactly 2 ... payloads ...

   `G1` measures “exactly 2 alert-API posts inside the completion block”. `MU1` changes the kind immediate, `MU2` changes the kind-1 payload base, `MU3` changes the kind-2 payload base. None changes the number or addresses of posts in the completion window. If a third post were inserted at, say, `0x4f0f80`, `G1` would fail but no named mutant reddens it. This violates “Every VERIFIED claim row must name the mutant that reddens it.” Add a real mutant that inserts/removes/changes a post inside `0x4f0f40-0x4f0fa0`.

3. **`NAMED.md:1478` — the slot-table row claims owner/text/bound facts, but `MU4-6` do not cover all of them.**  
   The row says:
   > payload `0x999ff4+4k`, owner `0x999fcc+4k`, text `0x99a01c+0x100k`, bound `k<=9`

   `G5` checks payload, owner, and clear arrays; `G6` checks the bound; `G7` checks two `shl 0x8` instructions. But:
   - `MU4` mutates only the payload array.
   - no mutant mutates the owner array `0x999fcc`.
   - no mutant mutates the text-slot base `0x99a01c` in the poster clear.
   - `G6` only checks `cmp ... ,0x9`; it does not check the following `jle`/branch, so “bound k<=9” is not fully read.

   Therefore the row’s `V MU4-6` is too broad. Either narrow the claim to what is actually mutated or add mutants for owner, text base, and branch direction.

4. **`scripts/m346_alert_raiser.py:318` / `NAMED.md:1480` — `G13` does not measure the claim “drainer READS both posted slots (1 at 5 sites, 2 at 2 sites)”.**  
   The gate only asserts a fixed list of addresses:
   ```python
   sorted(slot_reads) == [0x637340, 0x63734B, 0x63737D, 0x637388, 0x63738D, 0x6373B4, 0x6374B6]
   ```
   It does not distinguish slot 1 from slot 2, does not verify that those instructions are reads rather than pushes/leas/writes, and does not verify the claimed counts “5” and “2”. `MU12` only removes one address by changing `0x99a21c` to `0x99a31c`; it does not prove the 5/2 split or read semantics. The claim is stronger than the gate.

5. **`scripts/m346_alert_raiser.py:326` / `NAMED.md:1481` — the retraction row claims “not a queue (no head/count)”, but `G16` does not measure absence of head/count.**  
   `G16` only counts first-byte writers of text slots. A queue can exist without first-byte writers: head, tail, count, ring index, or a separate control block could still exist. The gate does not scan for queue-control globals, does not read a head/count structure, and does not prove “no head/tail/count”. The prose claim is broader than the measurement. Either weaken the claim to “no first-byte writers other than posters/drainer” or add a real gate that reads the absence of queue-control fields.

P2 findings

6. **`scripts/m346_alert_raiser.py:297` / `NAMED.md:1477` — `G1`’s window does not match the prose “after the pop 0x4ef5d0 @0x4f0f46”.**  
   The gate uses:
   ```python
   0x4F0F40 <= p[0] <= 0x4F0FA0
   ```
   That starts six bytes before the claimed pop at `0x4f0f46`, and the script never verifies that `0x4f0f46` is `call 0x4ef5d0`. The claim is anchored to the pop; the measurement is anchored to an arbitrary nearby window. This is a definition mismatch. Anchor the window to the measured pop instruction, or explicitly claim only the fixed address window.

7. **`scripts/m346_alert_raiser.py:261` / `NAMED.md:1479` — `G9` does not prove “every text-slot read is `0x99a01c + (k<<8)`”.**  
   `stride_ok` only checks that each matching `add ...,0x99a01c` is preceded by some `shl ...,0x8`:
   ```python
   INS[POS[r[0]] - 1][1] == "shl" and "0x8" in INS[POS[r[0]] - 1][2]
   ```
   It does not verify that the shifted register is the same register used in the `add`, nor that the shifted value is the slot index, nor that the instruction is a read. A mutation changing `shl edx,0x8; add eax,0x99a01c` to unrelated registers could still pass. The gate is weaker than the claim.

8. **`scripts/m346_alert_raiser.py:305` / `NAMED.md:1480` — `G12` claims “re-loops on strlen(slot1)>0x10” but does not read the loop or `strlen`.**  
   The gate checks:
   - five calls to `0x5f1394`
   - `call 0x5f1394` at `0x63732d`
   - `push 0x99a11c`
   - `cmp eax,0x10`

   It does not verify that `0x64c460` is `strlen`, does not verify the branch forms a loop, and does not verify that the loop condition is based on the result of that `strlen`. The “re-loops” part is not gated.

9. **`scripts/m346_named_rotate.py:118` — the rotate script’s idempotence check is wrong and can double-rotate.**  
   It checks:
   ```python
   if "stub governs" in lines[s]:
   ```
   where `lines[s]` is the `## M313` header line. In the produced stub, `this stub governs` is the final line of the stub, not the header. Running the script again will not skip; it will treat the stub as the original block, overwrite the archive with the stub, and replace the stub with a stub of the stub. This is a real tool defect in a rotation script that is supposed to be safe/idempotent.
