Findings, most important first.

1. **P1 — G10 does not gate the feeder input law it marks VERIFIED.**  
   `NAMED.md:M330 claim row “feeder 4f47f0 … v=[984d48+48*slot] (bits 95da9c) … E-=v,+300+=v”` is marked `V` citing `G10` (`evidence/m330_block300_census.txt:58-59`). But `scripts/m330_block300_census.py:404-437` only pins the `0x984d48` base load, owner/faction bytes, halving arithmetic, and ENERGY/+300 update. It never reads or proves:
   - slot-array scaling `48*slot`,
   - slot range `1..34`,
   - base flag-bit source `0x95da9c`,
   - the skip/iteration loop that selects slots.
   Thus G10 can stay green if the feeder actually reads from a different array, stride, or slot set. MU9/MU10 only mutate the subtract/halving endpoints (`scripts/m330_mutate.py:35-36`), so this VERIFIED claim is not actually gated by its cited mutant set.

2. **P1 — “refund NOT faction-masked / VACUOUS” is asserted from loop bytes, not from the value actually reaching the mask gate.**  
   `NAMED.md` claims mask gate VACUOUS (`cl=8`) and `G6` marks it V. The gate at `scripts/m330_block300_census.py:256-283` pins a loop and computes `cl_final = 1 + (cmp_bound - 0x94f70c)/STRIDE`, but it does not prove that the loop is the one executed before the refund, nor that `[ebp-4]` is not overwritten between the loop and the `mov ecx,[ebp-4]` pin. In particular, it does not scan for stores to `[ebp-0x4]` in the window from loop exit to `0x5206fd`. So the claimed endpoint (`cl` at refund) is only inferred, not read from the full path definition.

3. **P2 — Entry-zero claim is not fully gated: `xor eax,eax` and zero stores are pinned, but register liveness is not.**  
   `scripts/m330_block300_census.py:302-314` verifies `xor eax,eax` at `0x520557` and four stores to `+3f8/+2fc/+300/+308`. It does not verify that `eax` remains zero across the gaps between `0x520557` and the stores, nor that no branch into the middle of that sequence changes the source. Therefore the prose “entry zeroes …” overstates what the gate actually reads from bytes.

4. **P2 — `5362f5` “both block-offset folds” is not fully read by `G12`.**  
   `scripts/m330_block300_census.py:456-485` proves `2095*arg3` and `8380*edi` stores to `[ebp-0x14]`, and pins `mov esi,[ebp-0x14]` at `0x5362b1`, but it does not prove that `esi` survives unchanged to the actual field access at `0x5362f5`, nor that the `[ebp+0xc]` value used to build `2095*arg3` is not clobbered between `0x535c90` and `0x535cc3`. The arg-fed provenance claim therefore depends on unmeasured windows.

5. **P2 — `54b367` block provenance proof is weaker than the claim.**  
   `scripts/m330_block300_census.py:456-467` pins the fold to `[ebp+0x8]` and checks that `[ebp+0x8]` is not stored between `0x54b1e6` and `0x54b35c`. But it does not verify that execution actually reaches `0x54b35c` before `0x54b367`, nor that `edx` is not set by some other path after `0x54b35c` and before `0x54b367`. So the “last-overwrite law” result is asserted more strongly than the instrument checks.

6. **P2 — The mask mutation coverage is too narrow for the “VACUOUS” claim.**  
   `scripts/m330_mutate.py:30` reddens G6/R only by patching the loop-bound compare at `0x52062f`. That proves the current authored bound matters, but it does not exercise a patch that forces a non-zero `cl` reaching the gate through another path. Given the missing liveness/control-flow checks in G6 (`scripts/m330_block300_census.py:268-283`), the claimed VACUOUS property is not robustly reddened by a mutation on the real instruction window.

7. **P2 — `G3` reader gate does not actually verify reader operands, only opcodes.**  
   `scripts/m330_block300_census.py:226-236` checks that all pinned reader addresses start with `mov` or `sub`; it does not check that they read from the pinned `+300` addresses or that register forms match the census hits. The detailed PASS text claims “7 STRIDE readers” and identifies their roles, but `G3` itself is mostly a name-check. The reader facts are carried elsewhere (`G1`/`G4`), so this is not fatal, but the gate as written is weaker than its prose.

8. **P2 — `G4` sign-fix pinning is under-specified.**  
   `scripts/m330_block300_census.py:205-217` checks that a `shr` exists with immediate `0x1f` and that a following `add` exists, but it does not verify the shifted register is the high half of the magic product, nor that the added value comes from the correct source. The numeric model is tested independently (`magic_div3`), but the bytes only partially constrain the code shape being claimed.

9. **P2 — Digest-count claim is not fully evidenced in the new NAMED row.**  
   `NAMED.md` says “ACCEPT 13/13 digest 63def04aadb07bcf x3” and cites only `evidence/m330_block300_census.txt` and `evidence/m330_block300_census_rerun.txt` (`:66-67` each). That is two printed digests, not three. The digest is computed and printed by the instrument, so the number is real, but the “x3” claim lacks the third evidence citation.

10. **P2 — `ST 5/5` is marked V with “cite”, not an actual `path:line`.**  
   In the M330 ACCEPT row (`NAMED.md`), the harness and census evidence are cited, but `ST 5/5` is backed by the literal word “cite”. The repo convention requires path:line for VERIFIED rows. The self-test output exists at `evidence/m330_mutate_selftest.txt:1-6`, but the citation is missing.
