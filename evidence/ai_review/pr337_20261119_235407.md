# Adversarial Review: M327 (pick vii) PR

## P1 Blockers

### 1. `type_off_of` ignores the `ALGO=9` mutant — the instrument reads the type array from two different offsets under the same mutation
`scripts/m327_typeband_census.py:260` vs `:177`

`type_section` computes the type-array offset as `count_off + 4 + count_len + (3580 if ALGO == "9" else 3584)` (line 177). The helper `type_off_of` used inside `found_units_variants` for predicate C (line 260) hardcodes `+ 3584` with no `ALGO` branch.

**Why it matters:** When MU20 (`ALGO=9`) fires, the named-slot census (`prows`, `T1`, `T3`, `T4`) reads from offset `3580` but the mode-C found-units scan reads from offset `3584`. The two code paths disagree about which bytes are the type array, so any gate whose verdict depends on *both* (G5's `pfa,pfb,pfc` triple; G3's `hits_named == 67` when the C-mode named set diverges from the census) can behave inconsistently. In practice MU20 still reddens G1/G3/G4/G8/G9/G11 via other clauses, so the harness passes — but the instrument is measuring two different things under the same label. This is exactly the "the mutant doesn't apply uniformly" class of defect. Add the `ALGO` branch to `type_off_of` (or, better, pass the computed offset through instead of recomputing it).

### 2. G5's detail text asserts "C matches B on 4/4" but the gate condition never checks C against B on three of the four saves
`scripts/m327_typeband_census.py:364–368`

The gate:
```python
gate("G5", (pfa, pfb, pfc) == (67, 67, 67)
     and layout[POKED][3] == 67 and layout[POKED][4] == 49
     and all(layout[p][3] == layout[p][4] for p in SAVES if p != POKED), ...)
```
and the printed detail:
```
"exemption is load-bearing ONLY on m113map: 67 vs 49; 3/4 saves agree (the type-sound predicate C matches B on 4/4)"
```

For the three non-POKED, non-PRIMARY saves only A == B is checked. For POKED only A and B are checked. `fc` (predicate C) is compared to `fb` (predicate B) only on the PRIMARY. The parenthetical claim "C matches B on 4/4" is **not measured** by the gate — it is prose the gate prints. If a future save (or a real poke of `m112auto1`) made C ≠ B on a non-POKED save, G5 would still pass.

**Why it matters:** The whole point of predicate C in this instrument is to show that a type-sound check subsumes the coord exemption. The detail text makes a claim the gate doesn't verify. Either add `and all(layout[p][5] == layout[p][4] for p in SAVES)` (C==B on all four) or drop the parenthetical.

### 3. `poke_runs["covered"]` is a tautology — the "all diffs covered" clause in G6 can never fail
`scripts/m327_typeband_census.py:189–195`

```python
wins = sorted({(i // align) * align for i in diff})
wset = set(wins)
...
"covered": all((i // align) * align in wset for i in range(w, w + align)),
```

`w` is drawn from `wins`, so it is already in `wset`. For every `i` in `[w, w+align)`, `(i // align) * align == w` (because `w` is aligned to `align`), so the predicate is `w in wset`, which is true by construction. `covered` is always `True`; `cover_ok` is always `True`; G6's `cover_ok` conjunct is a tautology.

The prose says the poke law includes "every changed byte is covered by a window." That property is also true by construction (windows are derived from the diff bytes), so the instrument cannot measure it as stated — it is an identity. If the intent was "every byte in `[w, w+align)` differs" (a complete-window check), that would be `ndiff == align`, which is False for several windows (the evidence shows `ndiff=3` on many). Either way the current check measures nothing.

### 6. `type_section` is called twice on the primary, producing the `prows`/`punits` arrays from a redundant full save-parse
`scripts/m327_typeband_census.py:226`

```python
prows, punits = type_section(PRIMARY)[2], type_section(PRIMARY)[3]
```

`type_section(PRIMARY)` was already called at line 217 in the loop; its result is in `layout[PRIMARY]`. The double call re-parses the save (opening the file, reading all bytes, scanning 512 type records). More importantly for mutation correctness: if `M327_SAVE` env var causes `PRIMARY` to differ between the two calls (it cannot here, but the `ALGO`/`M327_ALGO` env is read inside `type_section` via a module-level global, so both calls see the same ALGO — this is fine), there's no divergence. But the pattern is fragile: any future change to `type_section` that introduces state or caching between calls would silently corrupt the census. Reuse `layout[PRIMARY]`.

### 8. The census header's "512×52-B type array at `count_off+4+count_len+3584`" description uses the same formula for both defining the offset and verifying it in G1
`scripts/m327_typeband_census.py:177, 351–354`

G1 checks:
```python
layout[p][1] == layout[p][0].count_off + 4 + layout[p][0].count_len + 3584
```
But `layout[p][1]` was assigned from `off` in `type_section`, which computes `off` using the identical expression. In a non-mutant run, this is `X == X` — a tautology. The gate can only fail via the gap (`== 4096`) and `closes` clauses. The claim "type array at count+4+len+3584" is therefore checked by construction rather than by an independent measurement. G1 isn't dead (gap and closes carry real weight, and MU20 reddens it via the offset mismatch), but the "type array at offset formula" component adds no independent verification.
