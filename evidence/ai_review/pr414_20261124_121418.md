P1 — `scripts/m382_treaty_readers.py:131-156` (`fold_2095`) and `:253-255` (`R2`): the “2095-fold / stride 0x20bc” claim is not actually measured. `fold_2095` only pattern-matches `shl A,6 / add A,B / lea C,[B+A*2] / shl C,4 / sub C,B` and then returns the constant `2095` from a formula that assumes `B == A`. For distinct `A`/`B` the sequence computes `2048*A + 47*B`, not `2095*owner + other`. It also never checks that the folded result is the index used by the field test, nor that the final address is `result*4 + 0x94d448`. So `R2` can pass on an unrelated or differently scaled address computation. This matters because the NAMED row “2095-fold (stride 0x20bc) at all 5 inline sites” is marked VERIFIED, but the shipped gate only proves a nearby byte pattern exists.

P2 — `scripts/m382_treaty_readers.py:111-127` (`census_register`) vs `NAMED.md:1652` (“def-use walked”): the implementation is not a def-use walk. It uses a fixed 8-instruction window after a `mov reg,DWORD PTR [..94d448]`, stops only on another `mov` of the same base, and ignores intervening writes (`xor`, `add`, `lea`, calls, branches, etc.). It can pair a load with a later test of a clobbered register or miss a use beyond the window. The prose says def-use; the instrument measures a bounded heuristic. This is a definition/window mismatch and can both overcount and undercount register readers.

P2 — `scripts/m382_treaty_readers.py:232-241` (`G5` polarity): the polarity extraction scans forward from each site to the first `jcc` without requiring it to be the branch immediately governed by the `test`, and without stopping at intervening flag-setting instructions or block boundaries.
