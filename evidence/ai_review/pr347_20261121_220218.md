2. `scripts/m333_nextprompt_trim.py:97-100` — region-B extraction moves from `B_MARK_START` to EOF
   ```python
   region_b = src[b1:].rstrip("\n")
   ...
   new = src[:a1] + A_NEW... + src[a2:b1] + B_NEW... + "\n"
   ```
   `b1` is the index of `M320/M323/M324 result one-liners VERBATIM...`. The script treats everything from that marker to EOF as the “result one-liner pointers” region and deletes it from `NEXT_PROMPT.md`. If any later `NEXT_PROMPT.md` section happens to follow that marker, it is silently archived and removed from the hot file. The `--verify` step then blesses that larger region as byte-exact, because it hashes exactly what the script moved.
   Why it matters: a cap-split tool should move a bounded region, not “from marker to EOF.” This is the same class of defect the PR itself claims to have fixed in the s312 rotation: hash-to-EOF regions are not safe once anything is appended later.

8. `scripts/m333_named_rotate.py:80-85` — `--restub` finds the M259 stub with a prefix search that can match non-governing text
   ```python
   a = src.index(STUB.split(" —")[0])
   ```
   The split prefix is just `## M259-M261`. If any other line, table row, or future stub mentions `## M259-M261`, `src.index()` may target the wrong occurrence. The script does not first assert that this is the rotated stub line containing `§rotation-1`.

   Rotate guards only with:

   and trim guards with both:
   ```python
   assert "§trim-s313-chain1" not in src
   ```
