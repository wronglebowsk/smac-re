P1 — `scripts/m355_laptop_masks.py:318-321` (`chk("G4b", ...)`) and `scripts/m355_mutate.py:31-48`  
**G4b is a green-only gate: no mutant can redden it.**  
G4b asserts the parser law from fixed byte patterns (`cmp 0x30`, `cmp 0x31`, `shl 1`, `lea +c-0x30`). The harness has no `M355_PATCH` or `M355_ALGO` that changes those bytes or the parser-law decoder. `MU12`/`MU13` only mutate the emit simulation and redden `G4c`, not `G4b`. This violates the mutation rule: a gate that stays green under its own harness is decoration. It matters because the claim “re-parsed by `0x628720`” depends on the parser law, but that law is not falsifiable by the shipped harness.

P1 — `scripts/m355_laptop_masks.py:286-297` (`chk("G1b", ...)`)  
**G1b does not actually verify the claimed argument decoding.**  
The printed claim and docstring say the 6-push windows resolve `app/file/key/default/out/size`. The gate only checks that the key names match and that no push value is `unknown`. It never asserts:

- `app == "Alpha Centauri"`,
- `file == ".\\Alpha Centauri.Ini"`,
- `default == 0x997120`,
- `out == 0x996a94`,
- `size == 0x100`.

A mutation that swaps `out`, `size`, `file`, or the default buffer can leave `G1b` green. The claim is therefore not gated as written.

`G1d` checks that the third pushed argument is `0x997120` and that the getter body contains some `mov BYTE PTR ds:0x997120,0x0`. P1 — `scripts/m355_laptop_masks.py:321-337` (`mask_arith`, `chk("G2a", ...)`)  
**The instrument never proves the masks are `Laptop`-derived.**  
`G1a` counts `Laptop` literal pushes. `G2` decodes `neg`/`sbb`/`and`/`add` in separate windows. There is no dataflow check connecting the `Laptop` `atoi` result to the register used by `neg`/`sbb`. The claim “`Laptop` = ... masks” is therefore only two independent measurements, not a verified causal link. A mutation that changes the `Laptop` push to another key while leaving the mask arithmetic intact would not redden `G2`; `MU5` only reddens `G1a`.

P2 — `scripts/m355_laptop_masks.py:355-367` (`chk("G3a", ...)`)  
**The Difficulty gate is not proven to be conditional.**  
`G3a` only requires that the loader window contains:

- a reference to `ds:0x92bde8`,
- `cmp eax,0x2`,
- some `jcc`,
- `or esi,0x20`.

It does not verify that the branch actually guards the `or`, nor that the `or` is executed only when `Difficulty < 2`. The prose claim is “`Difficulty`<2 ... ORs Preferences bit 5”, but the gate measures co-location, not control flow. Changing the branch target or condition may leave `G3a` green.

P2 — `scripts/m355_laptop_masks.py:370-391` (`emit_decode`, `chk("G4a", ...)`)  
**The emit-loop gate does not verify the mask register or the actual loop semantics.**  
`G4a` checks that the window contains `mov ...0x1f`, `cmp ...0x8`, pushes of `"1"`/`"0"`, and some `shl`/`test`. The simulation in `G4c` can be self-consistent while the real emit loop differs.

P2 — `scripts/m355_laptop_masks.py:403-418` (`chk("G5b", ...)`)  
**The field-map claim is broader than the assertion.**  
The NAMED/evidence claim says the decoded store order is `+0xa30<-A`, `+0xa34<-B`, `+0xa48<-C`, then A/B alternating across `+0xa38,+0xa3c,+0xa40,+0xa44,+0xa4c,+0xa50,+0xa54`, with `+0xa58<-B`. `G5b` only checks four entries:

```python
FIELD.get(0xA30) == GETTER_A
FIELD.get(0xA34) == GETTER_B
FIELD.get(0xA48) == GETTER_C
FIELD.get(0xA58) == GETTER_B
```

It does not assert the alternating pattern or the other fields. A mutation that swaps several A/B stores outside those four offsets can survive.

P2 — `scripts/m355_named_rotate.py:54-67` (`rotate()`)  
**The rotate script is not idempotent despite claiming to be.**  
After the first rotation, `NAMED.md` contains:

```md
## M293 (STUB - block VERBATIM: ...
```

`HEAD = "## M293 "` still matches this stub. A second run will treat the stub as the settled block, rewrite the archive with the stub, and destroy the byte-exact archived M293 block. The docstring says “rotate (idempotent)”, but the implementation can corrupt the archive.
