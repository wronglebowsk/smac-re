P1 — `sim/relations.py:437-441` — G1 does not gate the “five blocks + unconditional tail” claim.

The prose and NAMED row claim five `test bl` blocks (`0x7/0x1/0x10/0x17/0x1f`) plus an unconditional tail at `0x551bc7`. The gate only checks:

```python
preds[:4] == [0x7, 0x1, 0x10, 0x17]
```

It never asserts `preds[4] == 0x1f`, never asserts a sixth block with `pred is None`, and never asserts the tail address `0x551bc7`. The printed evidence shows those facts, but the shipped gate would still pass if the extractor dropped the `0x1f` block or mislocated the tail, as long as the first four predicates and the three clear immediates remained. That makes the V row “five `test bl` blocks … plus an UNCONDITIONAL tail” under-gated.

Why it matters: the central B36 claim is that the extracted program has this exact shape. A mutation that removes the `0x1f` block or moves the tail could leave G1 green, so the gate is not reading the claimed structure.

Why it matters: the rung’s main executable claim is parity against the dump. If the extractor can drift while parity stays green, the claim is decoration.

P1 — `sim/relations.py:521-543` — G5’s “war-only write always leaves the ladder empty” invariant is scoped too narrowly.

The check is:

```python
if (post & AT_WAR) and (post & (PACT | TREATY | TRUCE)) and (m & 0x17) == AT_WAR:
```

This only tests masks whose low-byte intersection with `0x17` is exactly `0x10`. It does not test masks such as `0x18`, `0x19`, `0x1a`, `0x1c`, etc., where `m & 0x17 == 0x10` but other low bits are present, nor does it test high-bit-only war masks combined with ladder bits in the pre-state in a way that distinguishes “war-only” from “war plus unrelated bits.”

The prose says “a war-only write always leaves the ladder empty.” The instrument’s definition of “war-only” is not the prose’s definition; it is a particular low-byte mask test.

Why it matters: the invariant can be green while the claimed law is not actually measured over the intended input class.

P2 — `sim/relations.py:300-325` — `program_classify()`’s `test`/`je`/`jne` decoding is only accidentally correct for single-bit tests.

The interpreter computes:

```python
zero = ~(cur & 0xFF) & int(ops.split(",")[1], 16)
```

and then treats truthy `zero` as “take `je`”. For a single-bit test this matches ZF semantics, but for a multi-bit `test` it does not. `je` should be taken only when `(operand & imm) == 0`, i.e. when all tested bits are absent. The current expression is true if any tested bit is absent.

G6 asserts there are three ladder tests and three want tests, but it does not assert that each immediate is a single bit. If the dump window changed to include a multi-bit test, the interpreter could silently mis-evaluate the chain while still agreeing with `Relations.classify()` by accident or failing in a misleading way.

Why it matters: this is an argument-decoding/control-flow bug in the instrument’s classifier interpreter, not just fragility.
