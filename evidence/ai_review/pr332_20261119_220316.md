P1: `evidence/m326_mutate.txt:4-27`, `scripts/m326_mutate.py:34-39`

The mutation harness is a declared-set checker, not an independent verifier of gate coverage.
It records each mutant’s actual reddened set (`red=...`), compares it with an authored
`declared` set, and only fails if they differ; it never checks that the declared set is
sufficient to make the claimed gate fail.

That is visible in `evidence/m326_mutate_measure.txt`, which proves the harness’s own
declared sets were initially wrong:

- `evidence/m326_mutate_measure.txt:18`
  `MU13 ... red=G1,G2,G6,G9 ... declared=G1,G2 ... MISMATCH`
- `evidence/m326_mutate_measure.txt:25`
  `MU23 ... red=G3 ... declared=G1,G2,G3 ... MISMATCH`

So at least two “OK” rows in the shipped evidence (`evidence/m326_mutate.txt:17`, `:22`) are
not real independent checks; they are assertions that the authors’ declared set happened to
match a measured sweep that already revealed two misdeclared mutants.

Why it matters: under the repo law, every `VERIFIED` row must be reddened by a mutant that
actually makes the claimed gate fail. Here the harness only enforces
`measured == authored`. If the authored set is too small or too large, the harness can be
“green” while some `VERIFIED` claim is either:

- not actually reddened by the claimed mutant, or
- only accidentally reddened by an unrelated collateral gate.

This is not cosmetic. It lets the PR certify rows against the wrong mutants. For example,
row 1 of `NAMED.md` (`NAMED.md:1297`) cites `MU4/9/12-17/19/20/23` for claims backed by
`G1-G3`, but the evidence shows `MU4` reddens only `G5` (`evidence/m326_mutate.txt:8`), not
`G1-G3`. The harness passes because `declared={G5}` equals measured `red={G5}`; it does not
catch that the claim-to-mutant mapping in `NAMED.md` is wrong.

This undermines the central anti-decoration mechanism for the PR.

P1: `NAMED.md:1298`, `scripts/m326_block224_census.py:875-880`, `evidence/m326_block224_census.txt:34`

is partly a definition mismatch with the gate.

`G1` pins:

- hit count = 13
- writers = 3
- readers = 10
- `n_abs == 0`
- `n_224 == 0`
- `n_sub == 0`
- writer sites == `[0x41a543, 0x520b22, 0x59f0c1]`

claim-to-gate scope mismatch the reviewer law is supposed to prevent.

P2: `NAMED.md:1301`, `scripts/m326_block224_census.py:892-906`, `evidence/m326_block224_census.txt:39`

The claim
> `all 10 readers = 220-224 AVAILABLE (itoa 64f980); cheat-cap MIN(g999fa4,avail)@41a4e0-f9`

is stronger than `G6` actually measures.

`G6` checks (`scripts/m326_block224_census.py:892-906`):

1. a hardcoded list of 10 triples exists;
2. each triple contains substrings `0x94d650` and `0x94d654`;
3. `len(triples) == len(readers)`;
4. one global `itoa` call shape at `0x416987/0x4169b5`;
5. one global cheat-cap shape at `0x41a4e0..0x41a4fe`.

That does not establish “all 10 readers = AVAILABLE” semantically.

Problems:

- The triple check is substring-based, not structural. It never proves the two loads feed the
  same base register, nor that the subtraction’s destination is the value ultimately used.
  A reader could read a 220 from one block context and a 224 from another and still satisfy
  the substring test.
- The `itoa` pin is only measured for one site. The prose ties `AVAILABLE` to `itoa` as if
  the reader set jointly establishes it, but `G6` only verifies one `push 0xa / call 0x64f980`
  instance (`:884-885`).
- The cheat-cap pin is only measured for one site. The wording makes it sound like a shared
  property of the reader law, but it is one local consumer check.

Why it matters: this is a source-only / partial-site measurement being sold as a whole-set
semantic claim. It passes for the current binary but does not actually read the claim in the
scope asserted by the prose.

P2: `scripts/m326_block224_census.py:620-627`, `scripts/m326_block224_census.py:700-704`

The resolver’s partial-register fix is incomplete: it treats only partial destinations as
opaque definitions of a wider queried register (`dest in PARTIALS.get(reg, ())`).

But the inverse case is missing:

- when `value_of(..., "al")` is asked, a full-register write to `eax` is **not** treated as a
  definition of `al`;
- same for `ax`, `si/di/bp/sp`, etc.

This is visible directly in the code path:

```python
if dest != reg:
    if ALGO != "7" and dest in PARTIALS.get(reg, ()):
        return ("lin", 1, 0, ("arg", reg))
    continue
```

So for `reg="al"`, `dest="eax"` does **not** match `PARTIALS["al"]` and is skipped.

Why it matters: this is the exact class of over-proof the PR claims to fix. Right now the
measured claims may survive because they mostly query full registers, but the instrument’s
own stated law (“partial-register writes are opaque”) is not implemented completely. That
makes future claims about leaf provenance fragile and potentially false.

P2: `scripts/m326_block224_census.py:679-749`, `scripts/m326_block224_census.py:752-797`

`seed_scan()` breaks on full-register redefinition of the seed register, but not on
partial-register redefinition of that same seed register:

```python
d2 = reg_of(parts2[0])
if d2 == dest and mn2 not in ("cmp", "test"):
    break
```

Again, this misses the inverse subreg case:

- seed register = `eax`
- intervening instruction = `mov al, ...`

The scanner will continue treating `[eax+d]` as still tracking the original address, even
though the low byte changed and the full address is no longer known.

Why it matters: `G3` pins the seed-access totals and “sibling-offset-into-224=0”
(`scripts/m326_block224_census.py:871-876`, `evidence/m326_block224_census.txt:36`). The
seed scanner is the instrument that justifies that claim, but it can keep a stale seed past
a partial invalidation. That is a real correctness gap in the measurement, not just a
theoretical robustness issue.
