## Findings

1. **P1 — `NAMED.md` M343 row 2 misstates the vtable slot for `FUN_005f58fa`**  
   `NAMED.md` (new M343 table, row 2) says:

   > `FUN_005f58fa` (+0x64 of all six family vtables) x3

   But the instrument and evidence say otherwise. `scripts/m343_a40_writer.py` builds `SLOTS[SIB64]` and gate `G2` asserts:

   ```python
   [s for _v, _n, s in SLOTS[SIB64]] == [0x64, 0x6C, 0x64, 0x64, 0x64, 0x64]
   ```

   and `evidence/m343_a40_writer.txt:26` prints:

   > `0x5f58fa = +0x64 of class 0x67164c, +0x6c of CPane subobj 0x671644, ...`

   So the claim is false as written: it is **not** `+0x64` of all six; the `CPane` subobject slot is `+0x6c`. This matters because the row is marked `V`, and the prose claim does not match the measured fact. The same wrong wording is repeated in `SESSION_NOTES.md` and `NEXT_PROMPT.md`.

2. **P1 — `FUN_005f5a11` “receiver `ds:0x9977f0`” is not actually gated as a receiver fact**  
   `NAMED.md` M343 row 2 claims:

   > `FUN_005f5a11` (receiver `ds:0x9977f0`) x2

   The store count is gated by `G4`, but the receiver identity is only weakly gated by `G7`. `G7` checks:

   ```python
   BYADDR[0x5F3D70][2] == "DWORD PTR ds:0x9977f0,ecx"
   BYADDR[0x5F5A17][2] == "eax,ds:0x9977f0"
   BYADDR[0x5F3F45][2] == "eax,DWORD PTR [eax+0xa40]"
   BYADDR[0x5F3F3F][2] == "eax,DWORD PTR [ebp-0x394]"
   ```

   It does **not** prove that the `ecx` stored at `0x5f3d70` is the same object saved at `0x5f13b2`, nor does it prove that `FUN_005f5a11`’s receiver is the runner object rather than merely some object loaded from `ds:0x9977f0`. The claim says “same object,” but the gate only checks a few instruction strings. A mutation that preserves those strings while breaking the dataflow link would still pass. This is a real gate/claim mismatch for a `V` row.

3. **P1 — “ctor `FUN_00405ef0` = 0 refs” is only checked for field refs, not all displacement refs**  
   `NAMED.md` M343 row 2 claims:

   > ctor `FUN_00405ef0` = 0 refs

   But `G4` checks only:

   ```python
   "FUN_00405ef0" not in BY_FN
   ```

   `BY_FN` is built from `FIELD`, i.e. only non-indexed `[reg+0xa40]` refs. It does **not** check whether `FUN_00405ef0` has indexed refs such as `[x+y*1+0xa40]`. The census table lists indexed refs by function, but no gate asserts that `FUN_00405ef0` is absent from that indexed set. Therefore the gate does not read the claimed fact “0 refs”; it reads the weaker fact “0 field refs.”

4. **P1 — runner “1 READ, 0 stores” is also only checked over field refs**  
   `NAMED.md` M343 row 2 claims:

   > runner `FUN_005f1394` = 1 READ 0x5f3f45, 0 stores

   `G5` checks:

   ```python
   rr = BY_FN.get("FUN_005f1394", [])
   len(rr) == 1 and rr[0][0] == 0x5F3F45 and rr[0][3] == "READ"
   ```

   Again, `BY_FN` excludes indexed refs. If the runner had an indexed `[x+y*1+0xa40]` store, `G5` would still pass. The claim is about the runner’s total `0xa40` refs, but the gate measures only the field-ref subset.

5. **P2 — census claim includes “12 fns” and “complete for stores,” neither of which is gated**  
   `NAMED.md` M343 row 1 claims:

   > 97 refs name displacement 0xa40 = 25 indexed (12 fns) + 72 field, all dword ...; 0 `lea reg,[..+0xa40]` -> complete for stores

   `G1` checks only:

   ```python
   len(REFS) == 97 and len(SCALED) == 25 and len(FIELD) == 72
   and len(DSTORES) == 47 and len(DLOADS) == 25 and len(LEA) == 0
   ```

   It does not assert that the indexed refs span exactly 12 functions. More importantly, “complete for stores” is an inference from `len(LEA) == 0`, not a measured property. Stores could still evade the displacement census through pointer arithmetic, copied base registers, or other non-`lea` forms. The gate verifies the absence of one evasion form, not completeness.

6. **P2 — fingerprint claim “exactly 4 functions carry the pair” is not directly gated**  
   `NAMED.md` M343 row 3 claims:

   > receiver fingerprint = the PAIR ... exactly 4 functions carry it

   `G3` checks:

   ```python
   WRITER_FNS == ["FUN_005f5759", "FUN_005f58fa", "FUN_005f5a11"]
   and len(LOOSE) == 5
   and "FUN_005ee350" in LOOSE
   and "FUN_005eede6" in LOOSE
   and len(STORE_FNS) == 22
   ```

   It does not assert `sum(PAIR.values()) == 4`. The runner’s pair membership is not checked by `G3`, and `G5` only checks the runner’s field ref, not its fingerprint. So the exact “4 functions carry the pair” claim is not read by the gate.

7. **P2 — evidence citations for the fingerprint and identity rows are wrong or incomplete**  
   `NAMED.md` M343 row 3 cites:

   > `:28-38`

   for the fingerprint claim. But the decisive summary lines are:

   - `evidence/m343_a40_writer.txt:62` — functions carrying the PAIR
   - `:63` — WRITERS under the pair
   - `:64` — WRITERS under `>=3 of cluster`

   Lines `28-38` only show the first part of the table and do not contain the “exactly 4” or “wrongly admits 2 more” conclusion.

   Similarly, row 4 cites `:81-87` for the identity chain, but the first link printed in section E is at `:80`:

   ```text
   0x005f13b2 mov DWORD PTR [ebp-0x394],ecx
   ```

   The cited window omits the start of the claimed chain.

8. **P2 — value-law gate checks labels, not the semantic claim “container +0xec” / “resolver(container)”**  
   `NAMED.md` M343 row 5 claims:

   > each writer publishes {0 reset, `[container+0xec]` direct, `FUN_005fdcf7(container)`}

   `G6` checks exact strings such as:

   ```python
   "SELECTED eax+edx*1+0xec"
   "RESOLVER"
   ```

   But `chase()` labels any memory operand containing `+0xec]` as `SELECTED`, without proving the base is the dialog container. It labels a call as `RESOLVER` if the call target equals the hard-coded `RESOLVER = 0x5FDCF7`, without proving the argument is the container. The gate therefore verifies a heuristic provenance label, not the full semantic claim.

9. **P2 — M341 stub rows are marked `V` but do not name mutants**  
   The new M341 stub in `NAMED.md` has rows 1–6 marked `V`, but the stub table has no mutant column and names no mutants. The archived full table does name mutants, but the stub says:

   > this stub governs, one line per claim

   Under the repo convention, every `VERIFIED` claim row in `NAMED.md` must name the mutant that reddens it. The stub currently violates that convention. If the archive is intended to carry the mutant evidence, the stub should either include the mutant names or explicitly subordinate itself to the archived rows rather than saying “this stub governs.”

10. **P2 — ACCEPT row is marked `V` but names no mutant**  
   `NAMED.md` M343 row 6:

   > ACCEPT ... `PASS M343: 9/9` ... harness ... `NO-OP []` | V

   has no mutant. The convention says every `VERIFIED` claim row must name the mutant that reddens it. If ACCEPT rows are exempt, that should be explicit; otherwise this row is ungated by the mutation harness requirement.
