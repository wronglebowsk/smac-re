## Findings

1. **P1 — `scripts/m386_marker_pair.py:330-347` — G7 “0x20000 has 0 direct readers” measures the wrong field**
   The gate builds `inline` and `reg20000` from `rx`, i.e. references to `0x94d820` / the marker X field. But the claim is about the relations request bit `0x20000`, whose readers would be tests/compares against the relations dword (`0x94d448`-relative) or values loaded from it. The instrument therefore only proves that nobody tests the marker X coordinate for bit `0x20000`. A real reader such as `test DWORD PTR [edi+0x94d448],0x20000` would leave G7 green. This makes the NAMED row `0x20000: 0 readers, set alone...` (`NAMED.md:1644`) unverified by its cited gate.

2. **P1 — `scripts/m386_marker_pair.py:287-290` — G4 ebx-def-to-guard window stops too early**
   The gate says “no other write to ebx between the def and the guard”, but scans only:
   ```python
   ins[by[0x55532A]:by[0x555373]]
   ```
   The guard load is at `0x5553A4`. Any ebx overwrite between `0x555373` and `0x5553A4` is invisible to the gate. The claim that the guard’s base is still `0x20bc*esi` at the `jge` is therefore not fully read from the bytes.

3. **P1 — `scripts/m386_marker_pair.py:317-322` — G6 “all references are base-register-relative” is not actually gated**
   G6 checks:
   ```python
   absolute = [i.addr for i in ins if re.search(r'ds:0x94d82', i.ops)]
   formok = all(re.search(r'\[[^\]]*0x94d82[04]\]', i.ops) for i in rx + ry)
   ```
   That only rejects `ds:0x94d82...` forms and requires the field displacement to appear inside brackets. It does **not** require a base register. A direct absolute operand like `mov eax,DWORD PTR [0x94d820]` would satisfy `formok` and would not be caught by the `ds:` scan. The claim “all 54 references are base-register-relative [reg+0x94d820/824]” (`NAMED.md:1643`, evidence `evidence/m386_marker_pair.txt:112`) is therefore overclaimed.

4. **P1 — `scripts/m386_mutate.py:24-27` + `scripts/m386_marker_pair.py:330-347` — the `0x20000` “0 readers” claim has no real mutant**
   The only mutant touching G7 is MU7, which changes the treaty-clear mask. No mutant inserts a genuine `0x20000` reader against the relations dword, because the instrument does not scan that field. Under the repo rule, a gate that stays green under its own mutation is decoration. The row:
   ```text
   | 0x20000: 0 readers, set alone, cleared by 0xfffdfbff; gate = partner marker, noun INF | `:117` | V MU7 |
   ```
   (`NAMED.md:1644`) is not properly mutation-gated.

5. **P2 — `scripts/m386_marker_pair.py:214-223` — G2 “unit pair” does not pin that the stores use the loaded unit x/y**
   The gate checks that a `movsx edx,[eax+0x95da10]` and `movsx eax,[eax+0x95da12]` exist in the 8-instruction window before `0x558e0c`, and that a `shl eax,4` exists. It does not check that `0x558e0c` stores `edx` into `0x94d820` or that `0x558e12` stores `eax` into `0x94d824`. The claim “one pair takes a UNIT’s x,y” (`NAMED.md:1640`, evidence `evidence/m386_marker_pair.txt:50`) is only partially read.

6. **P2 — `scripts/m386_marker_pair.py:247-253` — G3 callee bounds claim is under-gated**
   The gate checks:
   ```python
   x1.ops.strip() == "edi,DWORD PTR [ebp+0xc]"
   "0x92a37c" in c1.ops
   "0x92a378" in c2.ops
   ```
   It does not verify that `c1`/`c2` are comparisons, that `c2` compares the x argument, or that the comparison direction implements `<`. The claim “FUN_004e34f0 bounds-checks arg1(y) < [0x92a37c] and arg0(x) < [0x92a378]” (`NAMED.md:1641`, evidence `evidence/m386_marker_pair.txt:74`) is stronger than the gate.

7. **P2 — `scripts/m386_marker_pair.py:352-355` — G7 “cleared by 0xfffdfbff” is not pinned to that mask**
   The gate only checks that the AND immediate does not contain `0x20000`:
   ```python
   chk(andm.mn == "and" and not (imm2(src(andm)) & 0x20000), ...)
   ```
   Any mask clearing bit `0x20000` passes. The prose/evidence specifically names `0xfffdfbff` (`NAMED.md:1644`, evidence `evidence/m386_marker_pair.txt:117`). The exact clearing mask is not verified.

8. **P2 — `NAMED.md:1643` — the “NOT deadline/counter” row omits the mutant that kills its RMW subclaim**
   The row claims:
   ```text
   NOT deadline/counter: 0 RMW, 0 0x985afc compares, 0 absolute ds: forms
   ```
   and names only `MU6 MU12`. `MU6` kills the turn-counter proximity part, `MU12` kills the absolute-form part, but the `0 RMW` part is killed by `MU5` (`scripts/m386_mutate.py:22-23`). Under the convention that every VERIFIED row names the mutant that reddens it, this row is incomplete.

9. **P2 — `scripts/m386_marker_pair.py:395-403` + `NAMED.md:1639` — the cited ACCEPT digest is not the pinned digest**
   G9 pins:
   ```python
   DIGEST_PIN = "deb7ca6b1006ecf6"
   ```
   and checks the table digest printed at `evidence/m386_marker_pair.txt:135`. But the milestone header cites the final PASS digest:
   ```text
   ACCEPT `scripts/m386_marker_pair.py` `59589b3a42bc1caa` (`evidence/m386_marker_pair.txt:137`)
   ```
   That final digest is computed and printed, but no gate pins `59589b3a42bc1caa`. If the finish/digest logic changes while the table digest remains pinned, the cited ACCEPT anchor can drift silently.

10. **P2 — `NAMED.md:1639-1645` — the new M386 table has no header row**
   The added M386 block starts directly with claim rows:
   ```text
   | PAIR: ... | `:35-50` | V MU1 MU2 MU10 MU11 |
   ```
   without:
   ```text
   | claim | ev | conf |
   |---|---|---|
   ```
   This is not merely cosmetic if the repo’s docs gate or downstream tooling expects claim tables to be parseable. It also makes the new block inconsistent with the remaining non-stub VERIFIED tables.
